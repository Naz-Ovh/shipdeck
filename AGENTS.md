# AGENTS.md

shipdeck: a TUI that builds locally, deploys over SSH as a systemd service and
rolls back any release. Design and decisions: `docs/plan.md`. Usage: `README.md`.

## Rules

- No commit, PR or file may carry an AI co-author line or a "generated by" note.
- Conventional Commits with a scope (`feat(engine): ...`, `fix(tui): ...`);
  the body says why. Small commits.
- Organise by subject. No `shared`, `common`, `kit`, `utils` or `helpers` modules.

## Replies

- Answer like one person to another in a casual chat: short, plain, quick to
  read. No walls of text.
- After building something: a short list of what is new.
- After fixing something: a before/after table of at most 3 rows, then one
  line of context.

## Layout

- `crates/engine/` (`shipdeck-engine`): `config` (deploy.yaml: types that
  are the JSON Schema, the line-aware YAML tree, the launch check, globs),
  `build` (version, local commands, ELF checks), `bundle` (picking files,
  tar.zst, unit), `ssh` (sessions,
  login, host keys, `~/.ssh/config` aliases), `remote` (server scripts; the backup and which files go in it),
  `release` (ids, release.json), `setup` (the server-setup.sh URL),
  `deploy` (the deploy and rollback flows, `report` for progress),
  `init` (the presets and the new deployable folder).
- `crates/tui/` (`shipdeck-tui`): the screens, dialogs and key handling.
- `crates/headless/` (`shipdeck-headless`): the `deploy`, `rollback` and
  `releases` commands for scripts and CI: plain lines, no questions, exit
  codes.
- `bin/shipdeck/`: the flags (clap lives only here), the login, the config
  check, then hands over to the TUI or headless. `init`'s questions live
  here too (`inquire`). The TUI and headless only
  show what the engine reports; neither depends on the other.

## Code

- No hacks or tricks. Do it the proper, documented way: the tool's own
  flag, format or API, or the spec. A guess that works on one machine fails
  on the next. When there is no proper way, say so instead of working
  around it.

- Every value that reaches a remote shell is either validated in
  `config/rules.rs`, checked with `release::is_safe_id`, or quoted with
  `ssh::sh_quote`. Keep it that way. The one exception is the `server`
  commands in `pipeline`: shell by design, written by whoever deploys and run
  as the deploy user.
- A config mistake is a `config::Problem` with the line it is on and a hint,
  never a bare string: shipdeck reports them all before it starts.
- The config types are the schema. Every field needs a doc comment (editors
  show it); after a change run `just schema`, which writes
  `deploy.schema.json` and the website's copy in `docs/website/public/`
  (a test fails until you do).
- Remote scripts are POSIX `sh`; they run through `sh -c`, whatever the login
  shell, after the variables the login shell's startup files export
  (`ssh::shell_env`, off with `ssh.shell_env: false` or `--no-shell-env`).
- The sudo commands in `remote::sudo_commands` are a contract with the sudoers
  line people install. Changing one breaks every existing server, and
  `server-setup.sh` must change with it (`setup_test.rs` checks they match).
- `server-setup.sh` at the repository root is public and runs as root through
  `curl | bash`, pinned to a release tag. It validates every argument before
  doing anything; keep it that way, and tag every release (`v<version>`).
- `.github/workflows/release.yml` is generated by dist from
  `dist-workspace.toml`. Change the toml and run `dist generate`; never edit
  the yml by hand.
- Tests and docs use neutral examples (`my-api`, `203.0.113.x`), never real
  hosts, IPs or project names.
- `examples/<kind>/deploy.yaml` must keep parsing and start with the schema
  line for this version (`config_test.rs` checks); a new field goes into the
  README table and an example.
- Release ids and the `current`/`releases`/`backups`/`shared` layout are a
  contract with servers already deployed to. Change them only on purpose.
- The exit codes in `shipdeck_headless::exit_code` are a contract with the scripts
  that call shipdeck. Add new ones; never renumber.
- Tests live next to the code in `<module>_test.rs`:
  `#[cfg(test)] #[path = "<module>_test.rs"] mod tests;`.
- Done means `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`
  and `cargo test --workspace` pass.
  lefthook's pre-push hook (`lefthook.yml`) runs them, with `cargo check`, on
  every push. There is no CI workflow on purpose: GitHub Actions only publish
  releases. Do not add one.
