Status and logs, for systemd and PM2

See whether the app is up and read its log, from the TUI or a script, the same way whichever manager runs it.

systemd and PM2 TUI and headless Stage 0: load the login environment
  • Status and logs work for both managers, in the TUI and in headless commands.
  • The engine reads them; the TUI and headless only show what it hands over, as with deploys.
  • Before anything else, remote scripts get the environment the login shell's startup files set (done).
  • Status is one word on the Deployables screen: systemctl is-active, or the PM2 state in the same words. It is fetched on s.
  • Logs appear only after a failed release: the last 30 lines (journalctl -n 30 through sudo, or pm2 logs --nostream). There is no way to follow them.
  • Headless has deploy, rollback and releases, but no status or logs.
  • PATH: a remote script is an SSH exec without a terminal, run with sh -c, so it reads no profile. A tool whose PATH is set in ~/.profile or ~/.bashrc (nvm, for one) is "not found", though a terminal finds it.

Once per connection shipdeck starts the login shell the way ssh <host> does for a terminal, $SHELL -i -l, which runs sh -c "export -p". POSIX prints the exported variables in a form sh reads back, so that text goes in front of every script as it is. Each shell reads its own files, so bash, zsh and fish all work, and shipdeck names no tool.

  • Checked on two Ubuntu 24.04 servers with zsh and nvm in ~/.bashrc: pm2, node and npm are found with it and not without.
  • Off with ssh.shell_env: false for one server, or --no-shell-env for a run.
  • A failing or slow (over 20 s) startup is a warning at preflight; commands then run without it.

Neither manager needs sudo for this.

The engine gets one remote::ServiceStatus: state, up since, release, and a list of instances (pid, state, restarts, CPU, memory). It replaces today's Status, which only has the state word.

The engine gets Server::logs(n) for the last lines and Server::follow_logs(n), which streams lines until it is dropped; dropping it closes the SSH channel, which stops journalctl -f or tail -F on the server. The failed-release view keeps using logs, with more lines.

Writing systemd output to files (StandardOutput=append:) is left out: it loses the journal's rotation, and the unit would need a writable log folder.

The deploy user cannot read another unit's journal on its own. Two ways:

With sudo, the two new commands go in their own list, not in remote::sudo_commands: a server set up before this still deploys, and only logs says "run server-setup.sh again". The 30-line command stays as it is, so nothing already installed breaks.

shipdeck status ./scripts/deploy [my-api ...] [--json] shipdeck logs ./scripts/deploy my-api [-n 200] [--follow]
  • status prints a table on stdout (or JSON with --json). Exit code 0 when every service is up, and a new code 6 when one is not. Codes are only added, never renumbered.
  • logs prints lines on stdout. With --follow it runs until Ctrl-C, then exits 0. PM2 cluster lines are prefixed with the instance.
  • Deployables: the service line becomes active · 4 instances · up 2h · 180 MB · 3% cpu · 0 restarts.
  • Logs screen (l, or tab 4): the last 200 lines, then it follows. ↑ ↓ scroll and pause, G follows again, esc goes back and stops the follow.
  • After a failure: the Operation screen says "l for logs".
