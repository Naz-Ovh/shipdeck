How shipdeck works, and where it goes

This is the agreed design. It shows the parts of shipdeck, what each part does and never does, how the parts talk, and why. The steps and their status are on the progress page. How today's features work in detail: README.md, docs/plan.md and shipdeck man.

  • Zoom Ctrl + scroll, or pinch with two fingers.
  • Go closer Double-click a frame, or pick it in the list on the left.
  • See all The ⤢ button at the bottom, or press 1.

In one minute

  1. All the work happens in one program: the engine.
  2. Every app you see (the TUI, the CLI, the desktop app, and later a web dashboard) is only a window on the engine. They talk with JSON messages, over stdin and stdout.
  3. The engine talks to your servers over SSH: one connection per server.
  4. On each server, a small helper, the agent, does the work. It is installed when you connect, and it exits when you leave.
  5. Work that must finish, like a deploy, is handed to systemd. So it keeps going if your laptop closes.
  6. Nothing new listens on the internet. SSH stays the only way in.
  7. It is built step by step: engine, desktop app, agent, domains, databases, ready-made apps, mail.

Each part

What each part does, and what it never does. The “never” list keeps the parts apart.

The apps

TUI · CLI · desktop · web later
your PCweb: in a browser

Does

  • Draws the screen and reads keys and clicks.
  • Sends messages to the engine, and shows what comes back.
  • Shows the engine's questions: a password, a new host key, “roll back?”.
  • The CLI also has the flags, the exit codes for CI, and shipdeck man.

Never

  • Opens SSH, builds, or reads and writes your files.
  • Makes a decision. The engine decides everything.

Talks to the engine with JSON messages: over stdin and stdout on your PC, over HTTPS for the web dashboard.

The protocol

a crate and a schema
crates/protocoldocs/schema/protocol.schema.json

Does

  • Lists every message, and what is inside each one.
  • Carries a version, so old and new apps can work with the engine.
  • Its schema makes the desktop app's C# types.
  • Has a client part that the TUI and the CLI use.

Never

  • Does any work. It is only the agreement.
  • Renames or removes a message. Messages are only added.

Cargo makes sure the apps depend only on the protocol, never on the engine itself.

The engine

shipdeck engine · no screen
your PClater: a home server, always on

Does

  • Reads the root file and every deploy file it lists, and finds every mistake, with the line and a hint.
  • Builds, packs, finds the files that changed, and uploads them.
  • Keeps a project up with systemd or PM2, or serves a static site with no process.
  • Holds the SSH connections, logins and host keys: one connection per server.
  • Checks the agent on every connection. Same-major versions are compatible; breaking changes require a major release.
  • Starts deploys and reports every step to the apps.
  • Keeps the offline copy on your PC, and fetches what is new from each server.
  • Later: opens an SSH tunnel to show database tables.

Never

  • Draws a screen, or asks a person directly. It asks through the app.
  • Does the work inside a server itself. The agent does that.

The agent

shipdeck-agent · on demand
each serveras your SSH userwhile you are connected

Does

  • Does file work itself: hash, receive, unpack, verify, link, back up, restore and remove.
  • Runs systemctl and PM2 directly with sudo -n only when the user is not root; reads status, releases and live logs.
  • Prepares and verifies releases while connected, then activates them as the final deployment phase. Interrupted files stay until the user approves cleanup.
  • Uses separate SSH channels for control messages and binary uploads. Writes are bounded so a dead receiver cannot hang a deploy.
  • Writes every event into state.db, each with a number, for shipdeck events and reconnect inspection.
  • Runs the server commands of your deploy file with sh.

Never

  • Builds anything. Nothing is ever built on the server.
  • Opens a port, or keeps running after you leave.
  • Becomes root on its own.

keepup

shipdeck-keepup · optional · later
each server, if installeda systemd service, always on

Does

  • Watches health, disk and services, even when nobody is connected.
  • Sends an alert when something is wrong.
  • When installed, it is the only program that writes state.db.
  • Does root work for the agent, but only if the server's owner allows it.

Never

  • Is needed for deploys. Everything works without it.
  • Opens a network port. It talks only over a unix socket.

not ours
every server

Already there

  • systemd: runs your project. Timers belong to later features; deployments run directly in the connected agent.
  • The journal: the raw logs.

How work flows

A deploy from start to end, and what happens when you leave.

A deploy, end to end

with the agent

Here the health check fails, and you answer “yes, roll back”.

Three kinds of long work

Each kind lives in a different place, so each one survives what it should.

While you watch

Runs inside the SSH connection, and ends when you leave. That is what you want for a log you were reading. Example: a live log.

Deployment preparation and activation

The connected agent prepares and verifies files, then activates the release. No background deploy job. A disconnect during preparation leaves the live release unchanged. Inspect interrupted activation on reconnect. Unfinished files stay until you approve cleanup.

Nobody connected, ever

A systemd service or timer, written once. systemd keeps it running, or starts it on time, like cron. Example: your project, nightly backups, certificate renewal.

When you leave

You close the app, or your laptop goes to sleep.

On your PC

  1. The app closes, so the engine's stdin closes.
  2. The engine takes no new work.
  3. It finishes the step that is running.
  4. Open questions get the safe answer: roll back; do not deploy a release that did not change; no password; do not trust a new host key.
  5. Then it exits.

On the server

  • No background deploy continues after disconnection.
  • Your deployed applications keep running under their manager.
  • Saved events remain in state.db. Unfinished files await approved cleanup.
  • The agent exits when the connection ends.
When you come back

The engine connects, starts the agent (and installs it if needed), reads saved events and inspects actual release state. An interrupted activation stays uncertain until checked.

Catching up

Every event on a server gets the next number. So nothing is missed.

Uploads and speed

  • Only the files the live release lacks are sent, packed with zstd. This works today.
  • Everything goes through the same SSH connection. There is no second protocol.
  • The speed limit is your internet's upload speed. An agent does not make the upload itself faster.
  • What the agent adds: it checks every file natively when it arrives, instead of through shell tools.
In short

The agent makes the work sturdier and easier to grow. It does not make your internet faster.

The protocol

How the apps and the engine talk. Later, the engine and the agent talk the same way.

The rules

  • JSON-RPC 2.0. One message per line, in UTF-8.
  • Only stdin and stdout. No port is opened. So only the app that started the engine can talk to it, and no token is needed.
  • stdout carries only messages. Everything else goes to stderr. Every child process gets an empty stdin.
  • Both sides ask. The app sends requests (deploy, list the releases). The engine sends events (a step started, a log line) and its own questions (a password, a new host key, roll back or not).
  • Only added, never renamed. initialize checks the protocol version and lists what this engine can do.
  • One deploy root per engine. workspace/open picks it.
  • Easy in every language. Fields are snake_case. A value with variants is one flat object with a kind field.
  • Errors. JSON-RPC's own codes for broken messages. shipdeck's codes start at -32001 and go down, listed once, never renumbered.
  • Secrets stay in the pipe. A password or passphrase is never written to a log.
  • The types are the schema. just protocol writes docs/schema/protocol.schema.json, and a test fails until it is current.
  • Own wire types. The engine maps its inner types onto the protocol's types. So a refactor never changes the wire by accident.

The desktop app

A native window, light and polished, with no Electron inside.

Built with

  • .NET 10, the long-term support version.
  • Avalonia with its Fluent theme: light and dark, following the system.
  • CommunityToolkit.Mvvm for the view models.
  • StreamJsonRpc with its newline-delimited handler and the SystemTextJsonFormatter.
  • Typed on both sides. The C# types are made from docs/schema/protocol.schema.json with NJsonSchema, and committed. just protocol makes them again.
  • A small, fast download. Built ahead of time (Native AOT). StreamJsonRpc is only partly ready for that, so the first build proves it. If it fails, the fallback is a trimmed, self-contained build.
  • The engine inside. Each download carries the shipdeck binary of the same version, and the app starts that one. So the two always agree.
  • Close guard. While a deploy runs, closing asks “Wait, or quit anyway?”.

Agent or no agent

Three ways shipdeck can work on a server, and why the on-demand agent won.

Three ways

No agent today

The engine sends shell commands over SSH and reads the text that comes back. Best when the features stay small.

On-demand agent chosen

The engine installs a small shipdeck program on the server and starts it over SSH, the way VS Code starts its server. Best when you want a real program on the server, with nothing running there after you leave.

Always-on agent only if needed

A root service on every server, running all the time. Best when you need access without SSH, like a hosted dashboard or a phone app.

The decision

The on-demand agent. It gives a real program on the server (typed requests, live events, Rust instead of shell) and keeps what makes shipdeck easy today: nothing to install by hand, nothing running when you leave, and SSH as the only door.

The always-on part is not ruled out. It comes as keepup, its own program that talks to the agent over a unix socket. So nothing has to be rewritten.

A contract

The release ids and the current, releases, backups and shared layout are a contract with servers already deployed to. They change only on purpose.

Which Linux

  • Plain deploys install nothing. They work on any Linux with systemd or PM2.
  • Guided setup installs what shipdeck itself needs (tar, zstd, coreutils, curl, sudo) from the Linux's own packages. What later features install (nginx, Docker) comes from the same package source.
  • Recommended order: Debian and Ubuntu first, then Rocky, Alma and Fedora (p4b1).
  • The agent reads /etc/os-release, and names a Linux it does not support yet, at setup.

Safety rules

  • Every value that reaches a remote shell is checked or quoted first. The only exception: the server commands people write in a deploy file, which run as the deploy user.
  • The agent never runs shell text that an app sends, except those same deploy-file commands.
  • Nothing opens a port. SSH keys and known_hosts stay the only way in.
  • The agent's messages are a contract like the engine's: only added, and the version is checked when the engine connects.
  • Servers without the agent keep the sudo lines they have today. That contract does not change.

Releases and install

How a release is built, and the ways people install shipdeck.

How a release is made

You push a tag; that is the only step. dist makes the release only after every binary is built and checked.

gnu or musl?

Linux builds
  • Why 2.28: GitHub's own actions need glibc 2.28 inside the build container, so an older floor breaks the build. Every glibc Linux from the last seven years gets the gnu build.
  • Why musl is not slower: musl builds use mimalloc instead of musl's own memory allocator.
  • A check fails the release if a gnu binary needs a newer glibc than 2.28.
