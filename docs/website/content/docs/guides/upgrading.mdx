## Install the new version

Run the same command you installed with:

- the install script: `curl -LsSf https://shipdeck.naz.ovh/install.sh | sh` again;
- cargo-binstall: `cargo binstall --git https://github.com/Naz-Ovh/shipdeck shipdeck` again;
- bin: `bin update shipdeck`;
- cargo: `cargo install --git https://github.com/Naz-Ovh/shipdeck --tag <tag> shipdeck`, with
  `--force` if cargo says the binary is already installed.

`shipdeck --version` prints the version you now run.
[Installation](/docs/getting-started/installation) has every way in.

## Update the schema line

Each config file can start with a schema line naming a release:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/Naz-Ovh/shipdeck/v<version>/docs/schema/deploy.schema.json
```

Change the tag to the new one, so your editor completes the new version's fields. If you map
the schema in `.vscode/settings.json` instead, update the URL there. shipdeck itself ignores
the line. [Config](/docs/reference/config#editor-completion) shows both.

## Config format 2

<Callout type="warn" title="This is a clean break">
The old config format is gone. There is no migration command and no compatibility mode: an
old file fails with unknown-key problems, which name the key and often the new one. Shipdeck
is in alpha, so this was done in one step.

A rollback to a release made with the old format is refused: "this release was made before
config format 2; deploy again".
</Callout>

What changed, in short:

| Old | Format 2 |
| --- | --- |
| A deploy root scanned for subfolders with `shipdeck.yaml` | One root file in the project folder (`-C` moves it, `-c` names another) |
| A deploy is a folder | A deploy is one file, anywhere |
| `shipdeck.yml` also accepted | `shipdeck.yaml` or `.shipdeck` only |
| App files (`apps: {admin: _admin.yaml}`) | Apps inline in the deploy file |
| `service.template` found next to `shipdeck.yaml` | `process.systemd.template`, a path you write |
| `project` (top) | The project folder: where you run shipdeck |
| `project` (app) | `apps.<app>.source` |
| `ssh`, `dir` | `server.ssh`, `server.dir` |
| `service`, `process_manager`, `start` | `apps.<app>.process` |
| `manager: systemd`, `process_manager.name` | the block itself: `systemd:`, `pm2:` or `oxmgr:` |
| `service.run_as` | `systemd.user` |
| A unit template was the only way to change the unit | `systemd.options`, by section |
| PM2 `options` silently replace shipdeck's `name` and `cwd` | An error |
| `static.root` (top) | `apps.<app>.static: true` and `apps.<app>.nginx.root` |
| `pipeline` | `release.steps` and `apps.<app>.steps` |
| `pipeline.pack.files.include.project` | `files` |
| `pipeline.pack.files.exclude.*` | `exclude` |
| `pipeline.pack.binary` | `apps.<app>.binary` |
| `run: {local, server}` | `local`, `server` on the step itself |
| `setup.check.server` | the end of `setup.server` |
| `health.check.*` | `health.local`, `health.server` |
| top `pipeline` copied into apps | nothing is copied |
| `release.json`, unit files at the release root | `.shipdeck/` |
| `shipdeck-monorepo.json` | `.shipdeck/settings.json` |
| `SHIPDECK_APP_DIR`, `SHIPDECK_FOLDER` | `{{ROOT}}`, `{{CONFIG}}`, and the same variables |
| `SHIPDECK_RELEASE` (the name) | `{{RELEASE_ID}}`; `{{RELEASE}}` is now the folder |
| Unit template `{{dir}}`, `{{workdir}}` and others | the placeholders in [Variables](/docs/reference/variables) |
| `pipeline.backup.keep` | `release.steps.backup.keep` |
| `failed.rollback` | `rollback.mode`, which adds `off` |
| A fixed 30-second rollback question | `rollback.ask_secs` |
| A rollback checks only the process state | It runs the restored release's health checks |
| A rollback by hand runs `done` | Every rollback runs `rollback`, then the restored release's setup (from a backup), health and done |
| `pipeline.backup.files.include`, `.exclude` | `steps.backup.include`, `.exclude` |
| `pipeline.backup.files.deployed` | Removed: a backup always holds what was uploaded |
| Rollback to a backup: unpack, set up, switch | Every step after upload, as for a fresh upload |

The whole design, with every rule and the reasoning, is in
[the config-v2 design page](https://github.com/Naz-Ovh/shipdeck/blob/main/docs/feature/config-v2.md).

### Doing it

1. Add a root file in the project folder:

   ```yaml title="shipdeck.yaml"
   root: true
   deploys:
     production: scripts/deploy/production.yaml
   ```

   A deploy's value can also be the deploy itself, written in place, instead of a file's path.

2. Turn each old deploy folder's `shipdeck.yaml` into one deploy file: `name`, `server`, and
   one entry per app under `apps`. `shipdeck init` writes a working file to start from.
3. Point commands at the deploy instead of the folder:
   `shipdeck deploy production`, `shipdeck rollback production <release>`.
4. Run `shipdeck tree production` to check what ships before you deploy.
5. Deploy once so the server has a release with `.shipdeck/settings.json`. Only then can a
   later rollback restore its settings.

## Login flags and server details

- `--key` is now `--key-file`, so it reads clearly next to `--key-text`. Change scripts and CI
  files. `--key` is an unknown option now.
- `--password`, `--key-text` and `--key-file` have no short form.
- New: `--host`/`-H`, `--port`/`-P` and `--user`/`-U`, and `SHIPDECK_SSH_HOST`,
  `SHIPDECK_SSH_PORT`, `SHIPDECK_SSH_USER`, for a run with one deploy.
- New: `${NAME}` in `server.ssh.host`, `port` and `user` of a deploy.
- New: `.env` in the project folder, or `--env-file`/`-E`. It fills `${NAME}`, `SHIPDECK_SSH_*`
  and the login variables. A variable in the real environment wins. Your commands do not get
  its values.

See [Server details outside the file](/docs/guides/ssh#server-details-outside-the-file).

## The agent's new folder

The server agent now keeps everything in `/var/lib/shipdeck`: its program, its log, and each
SSH user's events in `users/<user>/state.db`. It used to use `/opt/shipdeck/agent`,
`~/.shipdeck/state.db` and `~/.shipdeck-agent.log`.

The first connection installs the agent in the new place. Old events are not moved, so
`shipdeck events` starts empty. When you no longer need the old files, remove them on the
server:

```sh
sudo rm -rf /opt/shipdeck ~/.shipdeck ~/.shipdeck-agent.log
```

A server that mounts `/var` with `noexec` cannot run the agent from there.

## The setup helpers are gone

`shipdeck setup`, the TUI's `:setup` and `scripts/server-setup.sh` no longer exist.
Shipdeck installs and updates its agent on the first connection, and that needs root.

If you used `--access commands` or a sudo rule limited to some commands, give the
SSH user full password-free sudo instead. See
[Server access](/docs/guides/server-access). A user that is root, or already has
`NOPASSWD: ALL`, needs no change.

Units are installed from `current/.shipdeck/<process>.service`. A deploy does this by
itself.

## Read the release notes

The [releases on GitHub](https://github.com/Naz-Ovh/shipdeck/releases) say what changed.
shipdeck checks every config file it reads before it starts, so a key it no longer knows
shows up as a [config problem](/docs/reference/config-problems) with the line it is on,
before anything runs.
