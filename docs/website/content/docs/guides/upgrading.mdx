title: Upgrading
description: Install a newer shipdeck, point each deploy.yaml's schema line at the new tag, and renew the server's sudo rule when a release changes it.
---

## Install the new version

Run the same command you installed with:

- the install script: `curl -LsSf https://shipdeck.naz.ovh/install.sh | sh` again;
- cargo-binstall: `cargo binstall --git https://github.com/Naz-Ovh/shipdeck shipdeck` again;
- bin: `bin update shipdeck`;
- cargo: `cargo install --git https://github.com/Naz-Ovh/shipdeck --tag <tag> shipdeck`, with `--force` if cargo says the binary is already installed.

`shipdeck --version` prints the version you now run. [Installation](/docs/getting-started/installation) has every way in.

## Update the schema line

The schema line at the top of each `deploy.yaml` names a release:

```yaml title="deploy.yaml"
# yaml-language-server: $schema=https://raw.githubusercontent.com/Naz-Ovh/shipdeck/v<version>/deploy.schema.json
```

Change the tag to the new one, so your editor completes the new version's fields. If you map the schema in `.vscode/settings.json` instead, update the URL there. [deploy.yaml](/docs/reference/deploy-yaml#editor-completion) shows both. shipdeck itself ignores the line.

## Read the release notes

The [releases on GitHub](https://github.com/Naz-Ovh/shipdeck/releases) say what changed. shipdeck checks every `deploy.yaml` under the deploy root before it starts, so a key it no longer knows shows up as a [config problem](/docs/reference/config-problems) with the line it is on, before anything runs.

## Renew the sudo rule

If a release changes the sudo rule, run `server-setup.sh` from the new tag again, as root, on the servers that use it. Running it again changes nothing already in place and brings an older rule up to date. When a right is missing, shipdeck also names the command to run. See [Server access](/docs/guides/server-access).
