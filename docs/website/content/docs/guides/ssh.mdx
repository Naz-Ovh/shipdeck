---
title: SSH and login
description: How shipdeck finds the server, logs in, checks the host key and keeps one connection per server.
---

shipdeck talks to the server over SSH with its own client. It reads the target from `server.ssh` in the deploy file, can borrow settings from `~/.ssh/config`, and picks the login method from the command line.

## The target in a deploy file

`server.ssh` has three separate fields. There is no `user@host:port` form: write each part in its own field.

```yaml title="scripts/deploy/production.yaml"
server:
  ssh:
    host: 203.0.113.10   # an address, a DNS name, or a ~/.ssh/config alias
    user: deploy         # optional when the alias has User
    port: 2222           # optional; the alias's Port, else 22
```

| Field | Required | Default | Rule |
| --- | --- | --- | --- |
| `server.ssh.host` | yes | - | not empty |
| `server.ssh.user` | no | the alias's `User` | letters, digits, `.`, `_`, `-` only |
| `server.ssh.port` | no | the alias's `Port`, else `22` | an unquoted whole number, at most 65535 |

If neither `server.ssh.user` nor the alias gives a user, shipdeck reports at launch: `~/.ssh/config has no User for <host>`.

Screens show the target as `deploy@prod`, or `deploy@prod:2222` when the port is not 22.

## Using a ~/.ssh/config alias

Set `server.ssh.host` to an alias and shipdeck reads the matching entry:

```ini title="~/.ssh/config"
Host prod
  HostName 203.0.113.10
  User deploy
  Port 2222
  IdentityFile ~/.ssh/id_deploy
```

```yaml
server:
  ssh: { host: prod }
```

**Values in the deploy file win over the alias.** The address is the alias's `HostName`, else the written host; the port is the written port, else `Port`, else 22; the user is the written user, else `User`. When an alias is in use, the connect log line shows the real address: `connect deploy@prod → 203.0.113.10:2222 (...)`.

### What is read

| Keyword | Used for |
| --- | --- |
| `HostName` | the address to connect to (`%h` expands to the alias) |
| `Port` | the port, when `ssh.port` is not set |
| `User` | the user, when `ssh.user` is not set |
| `IdentityFile` | the key tried when you pass neither `--key-file` nor `--password`; only the first one counts |
| `Include` | read in place, relative to `~/.ssh`, with `*` and `?` in file names |

The matching follows `ssh`: lines before the first `Host` apply to every host, `*` and `?` wildcards and `!pattern` work, keywords are case-insensitive, and the first value found wins. `Keyword value` and `Keyword=value` are both accepted. In `IdentityFile`, `~`, `%d`, `%u` (`USER`, or `USERNAME` on Windows), `%h` and `%%` are expanded.

### What is not read

- `Match` blocks are never applied.
- An alias that needs `ProxyJump` or `ProxyCommand` is refused at launch:

  ```txt
  ~/.ssh/config reaches <host> through `ProxyJump bastion`, which shipdeck cannot follow yet; put the server's own address in server.ssh.host
  ```

- Any other keyword is ignored. No config file means no settings.

## Server details outside the file

A deploy file can stay free of real server details, so one file works on every PC and in CI.
There are three ways to give `host`, `port` and `user`.

1. **An alias.** The file says `host: shop-prod`. Each PC maps `shop-prod` in `~/.ssh/config`.
2. **A variable named in the file.** Your shell, justfile or `.env` sets it:

   ```yaml
   server:
     ssh:
       host: ${SHOP_PROD_HOST}
       port: ${SHOP_PROD_PORT}
       user: ${SHOP_PROD_USER}
     dir: /opt/shop
   ```

   Each deploy names its own variables, so the TUI and `deploy a b` work with many deploys.
   In flow-style YAML (`{ ... }`), write the value in quotes: `host: '${SHOP_PROD_HOST}'`.
3. **Flags or variables, for one deploy.**

   | Flag | Variable | Sets |
   | --- | --- | --- |
   | `--host`, `-H` | `SHIPDECK_SSH_HOST` | `server.ssh.host` |
   | `--port`, `-P` | `SHIPDECK_SSH_PORT` | `server.ssh.port` |
   | `--user`, `-U` | `SHIPDECK_SSH_USER` | `server.ssh.user` |

### Rules

- A flag wins over a `SHIPDECK_SSH_*` variable, and that wins over the file. A file value is
  read only when nothing above it is set. So a missing `${NAME}` is no error when `-H` replaces it.
- The flags and `SHIPDECK_SSH_*` need a run with exactly one deploy. With more (the TUI, or
  `shipdeck deploy a b`) they are an error that points to ways 1 and 2.
- The output says where a value came from when it is not the file: `host from --host`.
- `${NAME}` works only in `server.ssh.host`, `port` and `user`. Anywhere else it is plain text.
- A deploy whose variable is missing blocks only a run that uses it. In the TUI it shows as
  **unavailable**, with the reason, and the other deploys work.
- A name is letters, digits and `_`, and does not start with a digit. Text may surround it:
  `deploy-${TEAM}`.
- A variable that is not set, or is empty, is an error. It names the variable, the field and
  the deploy.
- After the replacement, `port` must be a number from 1 to 65535.
- `server.dir` comes only from the file.
- `{{HOST}}` and the release's `.shipdeck/settings.json` hold the final value.
- An alias works with every way: `-H shop-prod` reads `~/.ssh/config` like `host: shop-prod`.

### The `.env` file

- Shipdeck reads `.env` in the project folder when it exists. `--env-file <path>` (`-E`) reads
  that file instead. A relative path starts from the project folder. A named file that is
  missing is an error. Only one file is read.
- Its values fill `${NAME}`, `SHIPDECK_SSH_*`, and the login variables `SHIPDECK_PASSWORD`,
  `SHIPDECK_SSH_KEY`, `SHIPDECK_KEY_PASSPHRASE` and `SHIPDECK_SUDO_PASSWORD`.
- A variable in the real environment wins over `.env`.
- Your `local` and `server` commands do not get `.env` values. `.env` is never uploaded unless
  `files` lists it.

## Logging in

The login method comes from the command line, never from a config file. It applies to every deploy in the run.

| You run | shipdeck does |
| --- | --- |
| `shipdeck deploy production --key-file ~/.ssh/id_deploy` | logs in with that private key file |
| `shipdeck deploy production --password 's3cret'` | logs in with that password |
| `shipdeck` (the TUI) | tries the alias's `IdentityFile`; if there is none, or it is refused or unreadable, asks for a password in the screen |

`--key-file` and `--password` cannot be used together. `--key-file`, `--key-text` and `--password` have no short form: a password on the command line lands in your shell history, and `SHIPDECK_PASSWORD` or `.env` keeps it out. A leading `~` in `--key-file` is expanded by shipdeck, and a missing file stops at launch: `the key file <path> does not exist`.

<Callout type="warn" title="No ssh-agent">
shipdeck does not use ssh-agent, and it does not try default keys such as `~/.ssh/id_ed25519` on its own. Pass `--key-file`, or name the key with `IdentityFile` in `~/.ssh/config` (a `Host *` entry works). Key and password logins are supported, and `--passwordless` for a server that lets you in with neither (the SSH `none` login). Keyboard-interactive is not supported.
</Callout>

`--password` lands in your shell history. In zsh with `HIST_IGNORE_SPACE`, start the command with a space:

```sh
 shipdeck deploy production --password 's3cret'
```

### Passwords and passphrases in the screen

When a password is needed, the "SSH password" dialog asks for it:

<Screen title="SSH password">{`
╔ SSH password ════════════════════════════════════════════════════════════╗
║ Password for deploy@203.0.113.10                                         ║
║                                                                          ║
║  ••••••▏                                                                 ║
║                                                                          ║
║ Kept in memory for this run only; never written to disk.                 ║
║                                                                          ║
║  ⏎  log in     esc  cancel                                               ║
╚══════════════════════════════════════════════════════════════════════════╝
`}</Screen>

When the key was refused first, the prompt says so: `Password for <label> (key <path> was refused)`. An encrypted key file opens the "Key passphrase" dialog: `Passphrase for <path>`.

- You get 3 attempts; retries show ` (wrong, try again)`.
- What you type is kept in memory for this run only, so each password or passphrase is asked once: a password per `user@host` (with `:port` when the port is not 22, and the host as written), a passphrase per key file. Deploys that share that target share the password. A rejected one is forgotten.
- Failures read `<host> refused the password for user <user> 3 times` or `wrong passphrase for <path> 3 times`. Esc gives `login to <label> cancelled`.
- A refused key: `<host> refused the key <path> for user <user>`.

## Host keys

shipdeck checks the server's host key against `~/.ssh/known_hosts` (only that file), for the resolved address and port. Hashed entries are understood, and a port other than 22 uses `[host]:port` entries.

### First connection

An unknown server opens the "New server" dialog:

<Screen title="New server">{`
╔ New server ══════════════════════════════════════════════════════════════╗
║ First connection to [203.0.113.10]:2222                                  ║
║                                                                          ║
║ ssh-ed25519 key fingerprint                                              ║
║ SHA256:8vrt1yc2dRu4YFMqB5bIC4HImPqycsuGwrSVv8kl7cY                       ║
║                                                                          ║
║ Compare it with \`ssh-keygen -lf /etc/ssh/ssh_host_*_key.pub\` on the      ║
║ server. Trusting saves it to ~/.ssh/known_hosts.                         ║
║                                                                          ║
║  y  trust and connect     n  refuse                                      ║
╚══════════════════════════════════════════════════════════════════════════╝
`}</Screen>

1. On the server, run `ssh-keygen -lf /etc/ssh/ssh_host_*_key.pub` (through a console you already trust) and compare the `SHA256:` fingerprint.
2. Press `y` to trust and connect. shipdeck appends the key to `~/.ssh/known_hosts`, creating `~/.ssh` if needed.
3. Press `n`, Esc or Ctrl-C to refuse. The connection stops with `the host key of <host> was not trusted`.

shipdeck connects when you press `c` on a deploy, or when a deploy, the Releases screen or a rollback needs the server, so this dialog appears then.

### A changed key

If the server shows a different key of the same type, shipdeck refuses to connect:

```txt
HOST KEY CHANGED for <host>: it differs from line <n> of ~/.ssh/known_hosts. Someone could be intercepting the connection. If the server was reinstalled, remove that line and connect again.
```

If you reinstalled the server, delete that line (or run `ssh-keygen -R <host>`) and connect again to see the dialog.

### Host certificates

Host certificates are refused: `<host> offered a host certificate; only plain host keys are supported`.

## One session per server

shipdeck opens one SSH session per endpoint (host, port, user and key) and reuses it for status checks, the Releases listing, uploads and every deploy step. A closed session reconnects on the next use. Nothing connects until it is needed: `c` on the Deploys screen, a deploy, the Releases listing or a rollback. `c` on a connected deploy closes its session, so every deploy on the same `user@host:port` shows `not connected`.

- Connecting times out after 15 seconds: `connecting to <label> timed out after 15s`.
- Keepalives go out every 15 seconds.
- Every server action runs as `sh -c '<script>'`, so the user's login shell (bash, zsh, fish) does not matter.

## Deploying as any SSH user

shipdeck deploys as `server.ssh.user`, whoever that is. When the user is literally `root`, nothing goes through sudo. Any other user needs write access to `server.dir` (or the right to create it) and passwordless sudo for five commands per process, plus four more to stop, start or follow it from the TUI. [Server access](/docs/guides/server-access) covers the options and the setup script.
