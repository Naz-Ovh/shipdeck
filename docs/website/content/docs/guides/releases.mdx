Every deploy leaves a complete, named release on the server. shipdeck keeps the newest ones unpacked and ready, compresses older ones, and lets you switch back to any of them from the Releases screen.

## What a release is

A release is one folder, `releases/<id>` under `service.dir`. It holds everything the app needs to run:

- the binary, if `pipeline.pack.binary` is set;
- the files from `pipeline.pack.files`;
- whatever your setup commands added, such as `node_modules` or a virtualenv;
- `release.json`: the id, version, commit, whether the source was dirty, build time and who deployed it;
- `<service>.service`: this release's own systemd unit;
- a link for each `service.shared` folder, pointing at `shared/<folder>`.

Because each release installed its own dependencies at its own setup, a rollback finds them in place and setup is not run again.

### Release ids

```txt
v<version>-<git commit>[-dirty]-<UTC date.time>
```

For example `v0.3.1-ab12cd3-20261014.153012`: version `0.3.1` from your version file, commit `ab12cd3`, built on 14 October 2026 at 15:30:12 UTC. `-dirty` means tracked files had uncommitted changes when you deployed; untracked files do not count. Without git, the commit reads `nogit`. [Server layout](/docs/reference/server-layout#release-ids) has the exact rules.

## How many are kept

`service.keep` sets how many releases stay on the server:

```yaml title="deploy.yaml"
service:
  keep:
    open: 5          # unpacked in releases/, counting the live one. At least 1.
    compressed: 15   # as .tar.gz in backups/. 0 deletes older releases.
```

| Field | Default | Meaning |
| --- | --- | --- |
| `service.keep.open` | `5` | Releases kept unpacked and ready to switch to, counting the live one |
| `service.keep.compressed` | `15` | Older releases kept as `backups/<id>.tar.gz` |

With the defaults, up to 20 releases stay on the server.

shipdeck tidies in the **done** step of every successful deploy. It never tidies after a manual rollback.

1. The live release always stays open and takes one open slot.
2. The newest other open releases fill the remaining open slots. Newest means by the time in the release id, never by version text.
3. The open releases left over, together with the tarballs already in `backups/`, are sorted newest first. The first `keep.compressed` stay as tarballs: open ones among them are compressed. The rest are deleted.

For example, with `open: 5` and `compressed: 3`, releases 3 to 9 unpacked with 9 live, and tarballs of 1 and 2: releases 5 to 9 stay open, 4 and 3 are compressed, 2 stays as a tarball and the tarball of 1 is deleted.

The done step shows what it did, such as `2 compressed · 1 deleted`, or `3/5 open` when there was nothing to do. A tidying error is only a warning; the deploy stays live.

Releases are listed newest first. The `Where` column says where each one is:

| Where | Meaning |
| --- | --- |
| `LIVE` | `current` points at it. Marked with a green `●`. |
| `unpacked` | In `releases/`, ready to switch to. |
| `tar.gz` | Compressed in `backups/`. A rollback unpacks it first. |
| `not ours` | A folder in `releases/` that shipdeck did not name. |

A commit with a `*` (`ab12cd3*`) was built from a dirty working copy. `Size` is the disk use `du` reports on the server: the unpacked folder for an open release, the `.tar.gz` for a compressed one. The Details panel shows the counts against `service.keep` and, for the selected release, who deployed it and when (from its `release.json`; compressed releases do not show this).

Keys: `↑`/`↓` (or `k`/`j`) to select, `⏎` to roll back, `r` to read the list again, `Esc` to go back. See [Screens and keys](/docs/reference/screens).

## Rolling back by hand

Select a release and press `⏎`. A dialog names the release to roll back to and the one live now; `y` (or `⏎`) confirms, `n` or `Esc` cancels. shipdeck refuses the live release (`That release is already live`) and folders it did not create, and it runs one operation at a time.

A manual rollback runs these steps:

<Steps>
<Step>
### Connect

`Connect: checking the server`. shipdeck connects, checks the `sudo -n` rights as preflight does, and reads the releases again. It stops if the target is gone (`<id> is no longer on the server`) or already live.
</Step>
<Step>
### Unpack

Only for a compressed release: `Unpack: unpacking it from backups/`. The tarball is unpacked into `releases/<id>` through a hidden `.partial` folder, then removed, so the release is open again. For an open release this step is skipped (`already unpacked`). A failure here stops; nothing live changed.
</Step>
<Step>
### Switch

`current` points at the target, and the target's own unit is installed, with `daemon-reload` and `enable`.
</Step>
<Step>
### Restart

`systemctl restart <service>`.
</Step>
<Step>
### Health

The same probes, URL and checks as a deploy, with the same `timeout_secs`. If switch, restart or health fails, the same [rollback flow](/docs/guides/health-and-rollback#when-a-step-fails-after-the-switch) applies: shipdeck asks (or, with `rollback: auto`, does not) and puts back the release that was live before. The target is not deleted.
</Step>
<Step>
### Done

`pipeline.done` runs with `SHIPDECK_ACTION=rollback`. Old releases are not tidied. With no done commands the step is skipped (`nothing to run`).
</Step>
</Steps>

Setup commands do not run again: the target already has what its own setup installed. `pipeline.failed` runs if a step fails, as in a deploy.

## Folders shipdeck did not create

shipdeck lists a folder in `releases/` whose name is safe but is not a release id it made, such as `my-notes`, as `not ours`. It never compresses or deletes such folders, and it will not switch to them: `shipdeck did not create that folder, so it will not switch to it`. Folders and files starting with a dot are not listed at all; those are shipdeck's own transient files.

## Telling deploys and rollbacks apart

`pipeline.done` runs after a deploy and after a manual rollback. Use `SHIPDECK_ACTION` when a command should run only for one of them, or should say which it was:

```yaml title="deploy.yaml"
pipeline:
  done:
    run:
      local: ./notify.sh "my-api: $SHIPDECK_ACTION to $SHIPDECK_RELEASE (was $SHIPDECK_PREVIOUS)"
      server: '[ "$SHIPDECK_ACTION" = rollback ] || ./bin/warm-cache'
```

More in [Variables](/docs/reference/variables).
