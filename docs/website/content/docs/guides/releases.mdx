title: Releases

Every deploy leaves a complete, named release on the server, and a backup of what it
shipped. shipdeck keeps the newest releases unpacked and ready, keeps only the backup of
older ones, and lets you switch back to any of them from the Releases screen or from the
command line.

## What a release is

A release is one folder, `releases/<id>` under `dir`. It holds everything the apps need to
run:

- every file from `release.files` and each app's `files`, at the paths the config says;
- each app's binary, if it has one;
- whatever your setup commands added, such as `node_modules` or a virtualenv;
- `.shipdeck/release.json`: the id, version, commit, whether the source was dirty, build
  time and who deployed it;
- `.shipdeck/settings.json`: the resolved deploy, which a rollback reads;
- `.shipdeck/<process>.service` or `.shipdeck/<process>.pm2.json`: this release's own
  process file;
- a link for each shared folder, pointing into `shared/`.

Because each release installed its own dependencies at its own setup, a rollback to an
unpacked release finds them in place and setup is not run again. A rollback to a backup
runs setup again (see [below](#rolling-back-by-hand)).

### Release ids

```txt
v<version>-<git commit>[-dirty]-<UTC date.time>
```

For example `v0.3.1-ab12cd3-20261014.153012`: version `0.3.1` from your version file,
commit `ab12cd3`, built on 14 October 2026 at 15:30:12 UTC. `-dirty` means tracked files
had uncommitted changes when you deployed. Without git, the commit reads `nogit`.
[Server layout](/docs/reference/server-layout#release-ids) has the exact rules.

## Backups

Right after setup, the **backup** step packs the new release into `backups/<id>.tar.zst`,
on the server. Every release gets one, so the unpacked ones have a backup too. When a
release later leaves `releases/`, its backup stays, and a rollback can bring it back.

A backup always holds what was uploaded — every file from `files`, plus `.shipdeck/`.
Two lists change it:

```yaml title="production.yaml"
release:
  steps:
    backup:
      keep: { open: 5, compressed: 15 }
      include: [generated]                 # more paths setup made, in the release root
      exclude: [packages/big-fixtures]     # uploaded paths to leave out
apps:
  api:
    steps:
      backup:
        include: [dist/cache]              # paths in the app folder
```

- `include` adds paths that setup made on the server and cannot make again.
- `exclude` leaves out uploaded paths, such as big files you can do without on a rollback.
- An `include` pattern that matches nothing is a warning in the log, not a failure.
- A failure in this step removes nothing: the release folder stays and the live release
  was never touched.
- Shared folders are never in a backup.
- With `keep.compressed: 0` no backups are kept and the step says so.

## How many are kept

`release.steps.backup.keep` sets how many releases stay on the server:

```yaml
release:
  steps:
    backup:
      keep:
        open: 5          # unpacked in releases/, counting the live one. At least 1.
        compressed: 15   # only as their backup in backups/. 0 keeps none.
```

| Field | Default | Meaning |
| --- | --- | --- |
| `release.steps.backup.keep.open` | `5` | Releases kept unpacked and ready to switch to, counting the live one |
| `release.steps.backup.keep.compressed` | `15` | Older releases kept only as `backups/<id>.tar.zst` |

With the defaults, up to 20 releases stay on the server.

shipdeck tidies in the **done** step of every successful deploy. It never tidies after a
rollback.

1. The live release always stays open and takes one open slot.
2. The newest other open releases fill the remaining open slots. Newest means by the time
   in the release id, never by version text.
3. The next `keep.compressed` releases keep only their backup: their folder in `releases/`
   is deleted, the `.tar.zst` stays.
4. Anything older loses its folder and its backup.

The done step shows what it did, such as `2 backed up only · 1 deleted`, or `3/5 open`
when there was nothing to do. A tidying error is only a warning; the deploy stays live.

| Where | Meaning |

for the details, `r` to read the list again, `Esc` to go back. See
[Screens and keys](/docs/reference/screens).

## Rolling back by hand

Select a release and press `⏎`, or run `shipdeck rollback production <release>`. A dialog
names the release to roll back to and the one live now; `y` (or `⏎`) confirms, `n` or
`Esc` cancels. shipdeck refuses the live release (`That release is already live`) and
folders it did not create, and it runs one operation at a time.

A rollback runs these commands and actions:

<Steps>
<Step>
### Preflight

`Preflight: checking the server`. shipdeck connects, takes the project lock, and reads the
releases again. It stops if the target is gone (`<id> is no longer on the server`) or
already live. It reads the target's `.shipdeck/settings.json`; a release from before config
format 2 has none, and the rollback is refused with "this release was made before config
format 2; deploy again".
</Step>
<Step>
### Rollback

`Rollback: putting back <id>`. Your `rollback.server` commands run in `dir`, then
`rollback.local`. When they run, `current` still points at the release being replaced, and
`SHIPDECK_PREVIOUS` names the release being put back.
</Step>
<Step>
### Setup

Your `setup.server` commands from the restored release's `settings.json`, in its app
folders. This happens only when the release came back from a backup, because the backup
does not hold what setup made. An open release keeps what its own setup installed, and the
step says `already set up`.
</Step>
<Step>
### Switch, Restart, Nginx, Health, Done

`current` points at the target and its process files are installed; every process restarts;
`health.server` and each app's `health.url` must pass, with the restored release's own
timeout; then its `done` commands run in current.
</Step>
</Steps>

If the restored release fails its health check, the rollback ends as **rollback failed**
(exit code 5), and `failed` runs. The target is not deleted.

## Folders shipdeck did not create

shipdeck lists a folder in `releases/` whose name is safe but is not a release id it made,
such as `my-notes`, as `not ours`. It never compresses or deletes such folders, and it will
not switch to them: `shipdeck did not create that folder, so it will not switch to it`.
Folders and files starting with a dot are not listed at all; those are shipdeck's own
transient files.

## Telling deploys and rollbacks apart

`done` runs after a deploy and after a rollback. Use `SHIPDECK_ACTION` when a command
should run only for one of them:

```yaml
release:
  steps:
    done:
      local: ./notify.sh "shop: $SHIPDECK_ACTION to $SHIPDECK_RELEASE (was $SHIPDECK_PREVIOUS)"
```

More in [Variables](/docs/reference/variables).
