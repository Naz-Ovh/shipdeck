A deploy is always the same ten steps, in the same order. Some steps are shipdeck's own; the rest also run commands you write under `pipeline` in `deploy.yaml`.

<PipelineSteps />

Nothing live changes before **switch**. A failure in the first six steps stops the deploy and leaves the running release alone. A failure at switch, restart or health leads to putting the previous release back: after asking you by default, at once with `rollback: auto` (see [Health and rollback](/docs/guides/health-and-rollback)).

## The steps

### 1. Preflight

`Preflight: checking your PC and the server`

On your PC, shipdeck checks that the `project` folder exists and renders the systemd unit once with a sample release, so a mistake in `service.template` shows up now. Then it connects over SSH and reads the server's facts in one script: CPU architecture, glibc version, whether `service.dir` exists and is writable, free disk space, the live release and the service state.

On a first deploy it creates `service.dir`, as the SSH user, or with `sudo -n mkdir` and `chown` when the user has passwordless sudo. A `service.dir` that exists but is not writable stops here (`<user> cannot write to <dir>`). Then it checks:

- the `sudo -n` rights for the five commands it needs as root (skipped when you log in as `root`; see [Server access](/docs/guides/server-access));
- that `tar` and `zstd`, which unpack the release, are on the server. A server without them stops here with the command to install them (`apt install zstd`, or `dnf install zstd`);
- that the program `service.start` names, and every program in `pipeline.preflight.requires`, is on the server;
- that at least 100 MiB are free.

Then your commands: `pipeline.preflight.run.server` in `service.dir`, then `pipeline.preflight.run.local` in `project`. Last, shipdeck checks that every `pipeline.pack.files.include.deploy` pattern finds something.

A failure stops the deploy. Nothing was built or uploaded, and the live release was not touched.

### 2. Build

`Build: building on your PC`

shipdeck names the release first: version, short git commit, `-dirty` when tracked files have uncommitted changes, and the UTC time. From here on your commands see `SHIPDECK_RELEASE` and `SHIPDECK_VERSION`.

Then it runs `pipeline.build.run.local` in `project`. With no build commands it logs `pipeline.build.run.local is empty; shipping the files as they are`.

After the build it checks what was built: if `pipeline.pack.binary` is set, the binary's CPU and glibc floor are compared with the server's; every `pipeline.pack.files.include.project` pattern must find something.

A failure stops the deploy (`` the build failed: `npm run build` exited with code 1 ``). Nothing reached the server.

### 3. Pack

`Pack: packing the release`

shipdeck renders the real systemd unit and packs one `.tar.zst` in memory, compressed with zstd on every core: the binary (mode `0755`), `release.json`, `<service>.service` and the files you listed in `pipeline.pack.files`. Files whose name starts with `.env` get mode `0600`. Then it checks the server has room: about twice the archive plus its unpacked size.

No commands of yours run here. A failure stops the deploy. See [Packing files](/docs/guides/packing-files).

### 4. Upload

`Upload: sending the release`

shipdeck creates `releases/`, `backups/` and `shared/` in `service.dir` if they are missing, then uploads the archive to `releases/.<id>.tar.zst` over SFTP. When the server has no SFTP subsystem it falls back to `cat` over SSH.

A failure removes what was uploaded and stops.

### 5. Unpack

`Unpack: unpacking into releases/<id>`

The archive is unpacked into a hidden `releases/.<id>.partial` folder, then renamed to `releases/<id>`, so a half-written release never looks complete. Each `service.shared` folder is then linked into the release, pointing at `shared/<folder>`.

A failure removes the release and stops.

### 6. Setup

`Setup: setting up releases/<id>`

The new release is on the server but not live; the old one still serves. shipdeck runs `pipeline.setup.run.server`, then `pipeline.setup.check.server`, in `releases/<id>`. This is where you install dependencies or run migrations.

With no setup commands the step is skipped (`nothing to run`). A failure removes the new release, logs `releases/<id> was removed; <previous> is still live` and stops.

### 7. Switch

`Switch: making it the current release`

shipdeck points `current` at `releases/<id>` in one rename, then installs `current/<service>.service` to `/etc/systemd/system/`, runs `systemctl daemon-reload` and `systemctl enable`. The old process keeps running until the restart.

From here on, a failure leads to the [rollback flow](/docs/guides/health-and-rollback#when-a-step-fails-after-the-switch).

### 8. Restart

`Restart: <service>`

`systemctl restart <service>`. This is the only moment the app is down, usually a second or two. A failure leads to the rollback flow.

### 9. Health

`Health: waiting for the new release to settle`

shipdeck probes the service once a second until it is `active` (and `pipeline.health.url` answers, if set) three times in a row. Then it runs `pipeline.health.check.server` in `current`, then `pipeline.health.check.local` in `project`, retrying every 2 seconds until `timeout_secs`.

A failure leads to the rollback flow. [Health and rollback](/docs/guides/health-and-rollback) has the details.

### 10. Done

`Done: tidying old releases`

The release is live. shipdeck logs `<id> is live`, then tidies old releases as `service.keep` says (see [Releases](/docs/guides/releases)). Then it runs `pipeline.done.run.server` in `current`, then `pipeline.done.run.local` in `project`.

A failure here is only a warning (`pipeline.done: <error>; <id> stays live`). The step shows as warned, the deploy still counts as live, and `failed` does not run.

### Failed

`Failed: running pipeline.failed (after <step>)`

This step is listed only when `pipeline.failed.run.local` has commands. It runs after any run that ended with a failed step: stopped, rolled back, rollback failed, or kept live after a failure. It runs on your PC only, in `project`, because the server may be out of reach. `SHIPDECK_STEP` holds the step that failed and `SHIPDECK_ERROR` the first line of its error.

If nothing failed, it is skipped (`nothing failed`). Its own failure is logged as a warning and does not change the outcome.

## Summary

| # | Step | shipdeck does | your commands |
| --- | --- | --- | --- |
| 1 | preflight | checks your PC and the server | `run.server` → `run.local` |
| 2 | build | names the release | `run.local` |
| 3 | pack | packs the binary and files | - |
| 4 | upload | sends the archive to the server | - |
| 5 | unpack | unpacks it into `releases/<id>`, links `service.shared` | - |
| 6 | setup | nothing: the old release is still live | `run.server` → `check.server` |
| 7 | switch | points `current` at `releases/<id>`, installs its unit | - |
| 8 | restart | restarts the service | - |
| 9 | health | waits until the service is active and `url` answers | `check.server` → `check.local` |
| 10 | done | tidies old releases (`service.keep`) | `run.server` → `run.local` |
| ✱ | failed | a step failed | `run.local` |

A step takes commands only where it can run them:

| Step | local | server | Server commands run in | Settings | If it fails |
| --- | --- | --- | --- | --- | --- |
| preflight | `run` | `run` | `service.dir` | `requires` | stops; nothing touched |
| build | `run` | ✘ | - | `version_from` | stops |
| pack | ✘ | ✘ | - | `binary`, `files` | stops |
| upload, unpack | ✘ | ✘ | - | - | the release is removed |
| setup | ✘ | `run`, `check` | `releases/<id>` | - | the release is removed; the old one keeps serving |
| switch, restart | ✘ | ✘ | - | - | asks, then rolls back |
| health | `check` | `check` | `current` | `url`, `timeout_secs`, `rollback` | asks, then rolls back |
| done | `run` | `run` | `current` | - | a warning only |
| failed | `run` | ✘ | - | - | logged |

Local commands always run in `project`. A key that is not in this table, such as `pipeline.build.run.server` or a step named `upload`, is refused before shipdeck starts (see [Config problems](/docs/reference/config-problems)).

## How commands run

Every command is one shell line, run with `sh -c`, so `&&`, pipes and `$VARS` work. Give one command or a list:

```yaml
pipeline:
  build:
    run:
      local: npm ci && npm run build     # one line
  setup:
    run:
      server:                            # a list, run in order
        - npm ci --omit=dev
        - npm run migrate
```

- **Each list item is its own shell.** A `cd` or `export` in one item does not carry into the next. Chain with `&&` when it must.
- **The first failure stops the list** and fails the step. A command fails when it exits with a code other than 0.
- **`run` commands run once.** **`check` commands must pass**: in setup they run once after `run`; in health they are retried every 2 seconds until `timeout_secs` runs out.
- When both sides run in one step, the server side goes first and the local side runs only if it passed.

**Local commands** run on your PC in `project`, with input from `/dev/null`. Their output streams into the log line by line. They get the [`SHIPDECK_*` variables](/docs/reference/variables) but not `service.env` or `service.env_file`.

**Server commands** run as the SSH user, each in a small POSIX `sh` script, whatever the login shell is. The script runs under `set -e`, changes into the step's folder, exports `service.env`, reads `service.env_file`, exports the `SHIPDECK_*` variables, then runs your command as written. They never run through `sudo`. See [Environment and secrets](/docs/guides/environment).

A failed command shows as `` `npm run migrate` exited with code 1 on the server `` (server) or `` `npm test` exited with code 1 `` (local).

## A worked example

A Node app: tests and a database check before anything else, a build on your PC, dependencies and migrations on the server while the old release serves, a health URL and a smoke test, and a message when it is live or when it fails.

```yaml title="scripts/deploy/my-api-prod/deploy.yaml"
# yaml-language-server: $schema=https://raw.githubusercontent.com/Naz-Ovh/shipdeck/v0.3.0/deploy.schema.json
name: My API (prod)
project: ../../..

ssh:
  host: prod
  user: deploy

service:
  name: my-api
  dir: /opt/my-api
  start: node dist/main.js
  env_file: .env
  env: { NODE_ENV: production }
  shared: [uploads]

pipeline:
  preflight:
    requires: [npm]
    run:
      server: pg_isready -q                 # the database answers
      local: [npm run lint, npm test]
  build:
    run:
      local: [npm ci, npm run build]
  pack:
    files:
      include:
        project: [dist, package.json, package-lock.json]
        deploy: [.env]
      exclude:
        project: ["**/*.map"]
  setup:
    run:
      server: [npm ci --omit=dev, npm run migrate]
    check:
      server: node --check dist/main.js
  health:
    url: http://127.0.0.1:3000/health
    check:
      server: ./bin/smoke-test
      local: curl -fsS https://api.example.com/health
    timeout_secs: 30
  done:
    run:
      local: ./notify.sh "my-api $SHIPDECK_VERSION is live"
  failed:
    run:
      local: './notify.sh "my-api failed at $SHIPDECK_STEP: $SHIPDECK_ERROR"'
```

What happens when you deploy it:

1. **Preflight** connects to `prod`, finds `node` and `npm`, runs `pg_isready -q` in `/opt/my-api`, then lint and tests on your PC. If the tests fail, nothing leaves your PC.
2. **Build** names the release from `package.json`, such as `v1.4.0-ab12cd3-20261014.153012`, then runs `npm ci` and `npm run build`.
3. **Pack**, **upload** and **unpack** put `dist/`, the package files and `.env` into `releases/v1.4.0-…`, with `uploads` linked to `shared/uploads`.
4. **Setup** installs production dependencies and runs migrations inside the new release. If a migration fails, the release is removed and the old one keeps serving.
5. **Switch** and **restart** make it live.
6. **Health** waits for three healthy probes of the URL, then runs the smoke test on the server and the public check on your PC, for up to 30 seconds in all.
7. **Done** tidies old releases and sends the message.

If anything fails, `failed` sends the step and the error. Because `node` is a bare name, shipdeck writes its full path into the unit, as found on the server.

<Callout type="warn" title="Migrations and rollback">
Setup runs before the switch, so a migration has already run when health fails and shipdeck rolls back. A rollback puts the old code back, not the old schema. Keep migrations compatible with the previous release.
</Callout>
