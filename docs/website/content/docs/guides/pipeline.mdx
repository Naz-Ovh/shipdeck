Every deploy runs the same twelve steps. Each step is **your commands first, then
shipdeck's action**. shipdeck's action is the work the step exists for.

<PipelineSteps />

## The steps

| # | Step | When | Shipdeck's action, after your commands |
| --- | --- | --- | --- |
| 1 | `preflight` | every deploy | checks the connection, `requires`, runners and permissions |
| 2 | `build` | every deploy | names the release, collects and hashes `files` |
| 3 | `upload` | every deploy | packs, sends, unpacks, links shared folders |
| 4 | `setup` | every deploy | none; the step is your commands |
| 5 | `backup` | every deploy | writes `backups/<id>.tar.zst` |
| 6 | `switch` | every deploy | points `current` at the new release |
| 7 | `restart` | every deploy | restarts each process |
| 8 | `nginx` | every deploy | parsed and checked; not built yet |
| 9 | `health` | every deploy | runs your checks and fetches `health.url` |
| 10 | `done` | every deploy | removes old releases beyond `backup.keep` |
| 11 | `rollback` | a failure in 6–9, or by hand | puts an older release back |
| 12 | `failed` | any failure | none; the step is your commands |

A deploy runs steps 1–10:

```text
preflight → build → upload → setup → backup
  → switch → restart → nginx → health → done

a failure in switch, restart, nginx or health:  → rollback → failed
a failure in any other step:                    → failed
```

## Your commands

Every step takes `local` and `server`, under `release.steps` and under
`apps.<app>.steps`. Leave a key out when there is nothing to run.

```yaml
release:
  steps:
    build:
      local: npm run build
apps:
  api:
    steps:
      setup:
        server: [npm ci --omit=dev, node --check dist/main.js]
```

Order inside a step: the server commands, then the local ones; the release's, then each
app's in name order. A failure fails the step, and shipdeck's action does not run. See
[Commands](/docs/reference/variables) for the runners and where each side runs.

## Notes

- **build:** the release is named when `build` starts, before your commands, so
  `{{RELEASE}}`, `{{RELEASE_ID}}` and `{{VERSION}}` work from `build` on.
- **health:** each try runs your commands, then fetches `health.url`. Apps are checked
  first, in name order; the release's commands run once every app is healthy.
- **failed:** `failed.server` runs only when the server can be reached. When it can't,
  the log says the commands were skipped and the local ones still run.
- **nginx:** not built yet. A deploy with `nginx:` on any app stops at preflight with
  "nginx management is not built yet".
- `setup.check` is gone: list the checks after the commands in `setup.server`.
- There is no `pack` step. What ships is `files`.

## Where server commands run

| Step | Release `server` | App `server` |
| --- | --- | --- |
| preflight, build, upload, rollback, failed | `{{ROOT}}` | `{{ROOT}}` |
| setup, backup, switch | `{{RELEASE}}` | `{{APP_RELEASE}}` |
| restart, nginx, health, done | `{{CURRENT}}` | `{{APP_CURRENT}}` |

Before `upload` the new release has no folder, so the first steps use `{{ROOT}}`.
`switch` commands run in the new release, which is not live yet. `rollback` and `failed`
use `{{ROOT}}`, because the folder they would use may be the broken one.

Local commands run in the project folder (release) and the app's `source` (app).
