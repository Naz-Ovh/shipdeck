The shipdeck repository has one complete example per kind of app in
[examples/](https://github.com/Naz-Ovh/shipdeck/tree/main/examples), each with a project
file (`shipdeck.yaml`) and a deploy file (`deploy.yaml`). Every file below is copied from
there, and a test reads all of them, so they stay valid.

Each example is a project folder you run shipdeck in:

```sh
cd examples/rust
shipdeck tree production
shipdeck deploy production
```

| Example | Ships | Built | Notable |
| --- | --- | --- | --- |
| Rust | a binary and `.env` | on your PC, against the server's glibc | `cargo zigbuild`, `health.url` |
| Go | a static binary, templates, `.env` and `config.yaml` | on your PC | `rollback.mode: auto` |
| Node.js | `dist` and the package files | on your PC; dependencies on the server | `requires`, `shared`, `setup`, `done` and `failed` |
| Python | the source | on the server, in `setup` | the whole project with excludes, `.venv` in the release |
| PM2 | `dist` and the package files | on your PC | `process.pm2.options`, cluster mode, no sudo |
| Static | `dist` | before the deploy | `static: true`, serving is yours |
| Monorepo | two apps in one release | on your PC | a process app and a static app together |

## Rust

A compiled service where only the binary and its `.env` travel.

```yaml title="examples/rust/deploy.yaml"
name: my-api
server:
  ssh: { host: prod, user: deploy }
  dir: /opt/my-api

apps:
  my-api:
    source: .
    files: [.env]
    binary: target/x86_64-unknown-linux-gnu/release/my-api
    process:
      systemd: {}
    steps:
      health:
        url: http://127.0.0.1:8080/health

release:
  steps:
    build:
      local: cargo zigbuild --release --target x86_64-unknown-linux-gnu.2.31
    health:
      timeout_secs: 30
```

- `build.local` uses [cargo-zigbuild](https://github.com/rust-cross/cargo-zigbuild) with
  the target `x86_64-unknown-linux-gnu.2.31`, so the binary needs at most glibc 2.31. Then
  the build step compares the binary's CPU and glibc with the server's and stops if they do
  not fit.
- `binary` names the file the build produces. It lands at `apps/my-api/my-api`, and the
  default `start` is `./my-api`.
- `health.url` is fetched on the server, so `127.0.0.1` works.

## Go

A static Go binary that needs nothing from the server.

```yaml title="examples/go/deploy.yaml"
name: worker
server:
  ssh: { host: prod }
  dir: /opt/worker

release:
  steps:
    preflight:
      local: go vet ./...
    build:
      local: CGO_ENABLED=0 go build -o dist/worker ./cmd/worker
    rollback:
      mode: auto

apps:
  worker:
    source: .
    files: [templates, config.yaml, .env]
    binary: dist/worker
    process:
      start: ./worker --config config.yaml
      env: { GOMAXPROCS: "2" }
      env_file: .env
      systemd: {}
    steps:
      health:
        server: ./worker healthcheck
```

- `CGO_ENABLED=0` makes a static binary, so the server needs no libc for it.
- `rollback.mode: auto` puts the previous release back without asking.
- `health.server` runs the app's own health command; there is no URL.

## Node.js

Built on your PC, with production dependencies installed on the server.

```yaml title="examples/node/deploy.yaml"
name: web
server:
  ssh: { host: prod }
  dir: /opt/web

release:
  steps:
    preflight:
      requires: [npm]
      local: npm test
    build:
      local: [npm ci, npm run build]
    backup:
      keep: { open: 3, compressed: 20 }
    done:
      local: ./notify.sh "web {{VERSION}} is live"
    failed:
      local: ./notify.sh "web failed at $SHIPDECK_STEP"

apps:
  web:
    source: .
    files: [dist, package.json, package-lock.json, .env]
    exclude: ["**/*.map"]
    shared: [uploads]
    process:
      start: node dist/main.js
      env: { NODE_ENV: production }
      env_file: .env
      systemd: {}
    steps:
      setup:
        server: [npm ci --omit=dev, npm run migrate]
      health:
        url: http://127.0.0.1:3000/health
```

- `requires: [npm]` makes preflight check that the server has npm.
- `setup.server` installs production dependencies in the new release while the old one
  still serves.
- `uploads` is a shared folder, kept in `shared/apps/web/uploads` and linked into every
  release.
- `done` and `failed` get `{{VERSION}}`, `$SHIPDECK_STEP` and the rest of the variables.

## Python

The source ships as it is; the server makes its virtualenv.

```yaml title="examples/python/deploy.yaml"
name: reports
server:
  ssh: { host: prod, user: deploy }
  dir: /opt/reports

release:
  steps:
    preflight:
      requires: [python3]
      local: python3 -m pytest -q

apps:
  reports:
    source: .
    files: [.]
    exclude: [tests, "**/__pycache__", .venv, "**/*.pyc"]
    process:
      start: .venv/bin/python -m app
      env_file: .env
      systemd: {}
    steps:
      setup:
        server:
          - python3 -m venv .venv
          - .venv/bin/pip install -q -r requirements.txt
      health:
        server: .venv/bin/python -c "import app"
```

- `files: [.]` ships the whole project; `exclude` leaves out tests and build leftovers.
- The server makes `.venv` in the release at `setup`, so the backup does not need it.

## PM2

PM2 runs the app as the SSH user, in cluster mode, without sudo.

```yaml title="examples/pm2/deploy.yaml"
name: my-api
server:
  ssh: { host: prod, shell_env: true }
  dir: /opt/my-api

apps:
  my-api:
    source: .
    files: [dist, package.json, package-lock.json, .env]
    process:
      start: node dist/main.js --port 3000
      env: { NODE_ENV: production }
      env_file: .env
      pm2:
        options: { instances: max, exec_mode: cluster, max_memory_restart: 300M }
    steps:
      setup:
        server: npm ci --omit=dev
      health:
        url: http://127.0.0.1:3000/health
```

- The manager is the block: `pm2:` instead of `systemd:`.
- `options` are PM2's own app settings. Shipdeck refuses the ones it writes itself: name,
  cwd, script, args, interpreter and env.
- With PM2 there is no sudo rule; guided setup starts that user's PM2 at boot instead.

## Static

Shipdeck ships the files and switches `current`. Serving them is up to you.

```yaml title="examples/static/deploy.yaml"
name: static-site
server:
  ssh: { host: prod, user: deploy }
  dir: /var/www/static

apps:
  site:
    source: .
    files: [dist]
    static: true
    steps:
      health:
        url: https://static.example.com/
```

- `static: true` means nothing runs on the server.
- Point your own web server at `<dir>/current/apps/site/dist`; the path does not change
  between releases.
- There is no restart and no process log.
- Add `nginx:` for shipdeck-managed serving once nginx is built. Today a deploy with
  `nginx:` stops at preflight.

## Several apps in one release

One deploy, one switch, one health gate.

```yaml title="examples/monorepo/deploy.yaml"
name: product
server:
  ssh: { host: prod, user: deploy }
  dir: /opt/product

release:
  steps:
    backup:
      keep: { open: 3, compressed: 15 }
    health:
      timeout_secs: 20

apps:
  api:
    source: api
    files: [api/server.js, api/.env]
    process:
      start: node server.js
      env: { PORT: "3000" }
      env_file: .env
      systemd: {}
    shared: [uploads]
    steps:
      health:
        url: http://127.0.0.1:3000/

  web:
    source: web
    files: [web/server.js]
    process:
      start: node server.js
      env: { PORT: "3001" }
      pm2: {}
    steps:
      health:
        url: http://127.0.0.1:3001/
```

- Apps run in name order: `api`, then `web`.
- Process names default to `<name>-<app>`: `product-api` and `product-web`.
- Each app has its own folder in the release: `apps/api`, `apps/web`.
