---
title: Environment and secrets
description: How an app's environment reaches it, how the env file is read, and where secrets and writable data live.
---

An app's process gets its environment from two places in `process:`: `env` for plain
values you can commit, and `env_file` for a file of secrets that ships with each release.
Server commands for that app load both; local commands load neither.

```yaml title="scripts/deploy/production.yaml"
apps:
  api:
    source: services/api
    files:
      - services/api/dist
      - { path: ./prod/.env, to: .env }   # ship the file that env_file names
    process:
      env_file: .env
      env:
        RUST_LOG: info
        PORT: 8080
```

## `process.env`

A map of variable names to values. Any YAML scalar is read as text, so `PORT: 8080` gives
`8080` and `DEBUG: no` gives `no`.

| Rule | Message when broken |
| --- | --- |
| Keys use letters, digits and `_`, and do not start with a digit | `` `<KEY>` is not a variable name `` |
| Values contain no `"`, `\` or newline | `` `env.<KEY>` must not contain quotes, backslashes or newlines `` |

The deploy file is committed, so keep secrets out of `env`. Values with quotes,
backslashes or newlines belong in the env file.

## `process.env_file`

A `KEY=value` file in the app folder, such as `.env`. The path is relative to the app
folder: no leading `/`, no `..`.

Nothing ties `env_file` to `files`: shipdeck does not check that the file is shipped.
Ship it yourself, usually with `to` from outside the source:

```yaml
files:
  - { path: ./prod/.env, to: .env }
```

Any shipped file whose name starts with `.env` gets mode `0600`.

```ini title="prod/.env"
# comments and blank lines are skipped
DATABASE_URL=postgres://api:secret@127.0.0.1/api
SESSION_KEY="k3y with spaces"
```

### How the process gets it

The built-in unit gets an `EnvironmentFile=` line for the env file, then one
`Environment=` line per `env` entry:

```ini title="/etc/systemd/system/<process>.service (part)"
Environment=SHIPDECK_RELEASE=<dir>/releases/<id>
EnvironmentFile=<dir>/current/apps/api/.env
Environment="PORT=8080"
Environment="RUST_LOG=info"
```

The path goes through `current`, so the service reads the env file of the release that is
live. A rollback brings back that release's own `.env`.

<Callout type="warn" title="Values in the unit file">
shipdeck writes `env` values into the unit as you wrote them. systemd gives `%` a meaning
in unit files, so a value with `%` belongs in the env file.
</Callout>

### How server commands read it

Server commands do not go through systemd. shipdeck loads the env file with its own small
reader that follows the rules of systemd's `EnvironmentFile=`:

- A missing file is skipped without an error.
- Blank lines and lines starting with `#` or `;` are skipped.
- A leading `export ` is removed.
- Lines without `=` are skipped, and so are lines whose key is not a variable name.
- One pair of surrounding `"` or `'` is removed from the value.
- Nothing is expanded: `$HOME` stays the literal text `$HOME`.

Which file a server command loads depends on the step. `preflight`, `build` and `upload`
read the live release's; `setup`, `backup` and `switch` read the new release's; `restart`,
`nginx`, `health` and `done` read the live one, which by then is the new release.

## Who gets which variables

| Variables | The process | Server commands | Local commands |
| --- | --- | --- | --- |
| `process.env` | yes | yes | no |
| `process.env_file` | yes | yes | no |
| `SHIPDECK_*` | no | yes | yes |
| shipdeck's own environment (your shell's) | no | no | yes |

For server commands the order is: the login shell's exports, then `env`, then the env
file, then `SHIPDECK_*`, which win over all. Each command runs as a separate script under
`set -e`, so an `export` in one list item does not reach the next.

Local commands run on your PC with your own environment plus the `SHIPDECK_*` variables.
They do not get the app's environment. When a local command needs a value from the app's
`.env`, load it in the command, for example
`set -a && . "../prod/.env" && set +a && ./notify.sh`.

The full list of placeholders and `SHIPDECK_*` variables is on
[Variables](/docs/reference/variables).

## Shared folders

A release is replaced on every deploy. Data the process writes and must keep, such as
uploads, goes in a shared folder:

```yaml
apps:
  api:
    shared: [uploads, data/cache]
```

At Upload, for each entry, shipdeck creates `<dir>/shared/apps/api/<entry>` the first
time, then makes `releases/<id>/apps/api/<entry>` a symlink to it. Every release sees the
same folder, and a rollback keeps the data.

<Files>
  <Folder name="/opt/my-api" defaultOpen>
    <File name="current → releases/v0.3.1-ab12cd3-20261014.153012" />
    <Folder name="releases" defaultOpen>
      <Folder name="v0.3.1-ab12cd3-20261014.153012" defaultOpen>
        <Folder name="apps" defaultOpen>
          <Folder name="api" defaultOpen>
            <File name=".shipdeck/" />
            <File name="uploads → /opt/my-api/shared/apps/api/uploads" />
          </Folder>
        </Folder>
      </Folder>
    </Folder>
    <Folder name="shared" defaultOpen>
      <Folder name="apps" defaultOpen>
        <Folder name="api" defaultOpen>
          <Folder name="uploads" />
        </Folder>
      </Folder>
    </Folder>
  </Folder>
</Files>

- Entries are folders relative to the app folder or the release root (for
  `release.shared`). A single shared file is not supported.
- Entries may not overlap: `data` and `data/cache` together are refused.
- A release must not contain a shared path: nothing may land in it.
- With the built-in unit the process can write only under `<dir>/shared`
  (`ProtectSystem=strict`, `ReadWritePaths=`), plus a private `/tmp`. Writable data belongs
  in a shared folder.

## Keeping secrets out of git

1. Put secrets in a `.env` file next to the deploy file, not in `process.env`.
2. Gitignore it.
3. Ship it with `to` and point `process.env_file` at it.

On the server the file lives in each release's app folder with mode `0600`, owned by the
SSH user. Config files themselves are never shipped.

<Callout title="When systemd.user is another user">
Release files and `shared/` belong to the SSH user. If the process runs as a different
user, it may not be able to open the `0600` `.env` itself or write to `shared/`. systemd
reads `EnvironmentFile=` before it switches user, so variables from the env file still
reach the process.
</Callout>
