---
title: Health and rollback
description: How shipdeck decides a new release is healthy, and what happens when switch, restart, nginx or health fails.
---

After the restart, shipdeck waits until every app proves it is up. If it does not, or if
switch, restart or nginx fails, shipdeck shows you the process log and puts the previous
release back, asking you first by default.

## How health decides

The health step has one time budget, `release.steps.health.timeout_secs` (default `20`,
at least `1`), counted from the start of the step.

<Steps>
<Step>
### Check each app, in name order

For each app, a try runs your `health.server` commands, then your `health.local` commands,
then, if the app sets `health.url`, fetches that URL **on the server** with
`curl -fsS --max-time 5`, or `wget -q -T 5` when there is no curl.

Because the URL is fetched on the server, a local address such as
`http://127.0.0.1:3000/health` works. Any 2xx answer passes; an error status or a refused
connection fails the try.
</Step>
<Step>
### Retry until the deadline

A failed try waits one second and runs again, until the budget is gone. When time runs
out: `app api was not healthy within 20s: <the last error>`.
</Step>
<Step>
### The release's own checks

Once every app is healthy, the release's `health.server` commands run, then its
`health.local`. They are retried the same way, inside the same budget.
</Step>
</Steps>

A static app has no process; without `health.url` its commands are all that is checked.

```yaml title="production.yaml"
release:
  steps:
    health:
      timeout_secs: 30                    # default 20
      server: test -d /opt/shop/shared/storage
apps:
  api:
    steps:
      health:
        url: http://127.0.0.1:3000/health   # fetched on the server
        server: ./bin/smoke-test            # in current/apps/api
        local: curl -fsS https://api.example.com/health
```

<Callout title="Pick a timeout that covers start-up and checks">
Every try runs your commands before the URL. If your app needs ten seconds to warm up and
your smoke test takes five, `timeout_secs: 20` leaves little room.
</Callout>

## A failure before the switch

A failure in preflight, build, upload, setup or backup never switched anything. The live
release keeps serving, and nothing is rolled back:

- preflight, build: nothing on the server changed.
- upload: the unfinished release files are kept for inspection (`shipdeck work`).
- setup, backup: the new release folder stays in `releases/`, and `current` still points at
  the old release. The run ends with exit code 1.

## A failure after the switch

Once `current` points at the new release, a failure at **switch**, **restart**, **nginx** or
**health** goes through one path.

1. The step turns red, and the full error goes to the log.
2. shipdeck reads the last 30 lines of the process log and writes them under
   `last log lines:`.
3. It decides whether to roll back, as `release.steps.rollback.mode` says.

### The rollback question

The dialog names the release that failed, the step and the error, and the release that was
live before. The countdown starts at `ask_secs` (default 30).

| You | What happens |
| --- | --- |
| press `y` | shipdeck rolls back now (`you chose to roll back`). |
| press `n` | The new release stays live as it is, so you can look at it. The log says `<id> stays live as you chose; roll back any time from the Releases screen`. Exit code 4. |
| do nothing for `ask_secs` | shipdeck rolls back (`no answer in 30s; rolling back`). |

If there is no screen to ask, shipdeck rolls back. Headless runs answer from
`--on-failure` (see [CLI](/docs/reference/cli)).

### Modes

```yaml title="production.yaml"
release:
  steps:
    rollback:
      mode: ask            # ask | auto | off. Default: ask
      ask_secs: 30         # with ask: roll back on its own after this
      keep_failed: false   # keep the failed release folder to inspect it
```

| Mode | What happens after a failure in switch, restart, nginx or health |
| --- | --- |
| `ask` | Ask, then roll back when the answer or the countdown says yes |
| `auto` | Roll back at once |
| `off` | Never roll back on its own; the failed release stays live, and you roll back by hand |

### What a rollback runs

`rollback.server` and `rollback.local` run first, then the action: unpack the target if it
only has a backup, run its `setup.server`, switch, restart, nginx, health with the
restored release's own checks, and `done`. After an automatic rollback, `failed` runs.
See the exact table in [Rollback](/docs/guides/releases#rolling-back-by-hand).

- If it comes back, the log says `<previous> is live again`. The failed release's folder is
  removed, unless `keep_failed: true`.
- If it does not, the run ends as **rollback failed**, and `failed` runs. The server needs
  your attention: look at `systemctl status <process>` and the journal there.

### The first deploy

When nothing was live before, there is nothing to roll back to. shipdeck logs
`nothing was live before, so there is nothing to roll back to` and stops. The failed
release stays live so you can look at it on the server.

## Outcomes

When a deploy ends, the banner on the Operation screen shows one of these:

| Badge | Meaning | Live afterwards |
| --- | --- | --- |
| `LIVE` | Every step passed. | the new release |
| `STOPPED` | A step failed before the switch, so the live release was not touched. | the release that was live before |
| `ROLLED BACK` | Switch, restart, nginx or health failed; the previous release is back. | the previous release |
| `KEPT` | Switch, restart, nginx or health failed, and you pressed `n`, or `mode: off`. | the new release, as it is |
| `ROLLBACK FAILED` | The new release failed, and putting the previous one back failed too. | unknown: check the server now |

A warning in the done step (a done command failed, or tidying failed) still ends as
`LIVE`.

<Callout type="warn" title="Rollback restores code, not data">
A rollback switches the release folder and the process files. It does not undo what setup
commands did to a database or to `shared/`. Keep migrations compatible with the release
before them.
</Callout>
