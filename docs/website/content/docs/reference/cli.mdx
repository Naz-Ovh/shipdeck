title: Command line
description: Every argument and flag of the shipdeck command, its errors, exit codes and what it prints.
---

You point shipdeck at a deploy root, it checks every `deploy.yaml` under it, and then opens the terminal UI. For scripts and CI, the `deploy`, `rollback` and `releases` commands do the same work [without the UI](#without-the-ui), and `man` prints [the manual](#the-manual).

## Synopsis

```txt
shipdeck [OPTIONS] <DEPLOY_ROOT>
shipdeck init     <DEPLOY_ROOT> [NAME] [--preset <PRESET>] [--manager systemd|pm2] [--host <HOST>] [--user <USER>] [--project <PATH>]
shipdeck deploy   <DEPLOY_ROOT> <NAME>... [--on-failure rollback|keep] [--allow-unchanged] [--trust-new-host]
shipdeck rollback <DEPLOY_ROOT> <NAME> --to <RELEASE> [--trust-new-host]
shipdeck releases <DEPLOY_ROOT> <NAME> [--trust-new-host]
shipdeck man      [index | configs | details <KEY>...]
shipdeck --schema
```

`deploy`, `rollback` and `releases` take the same login options as the screen: `--key`, `--key-text`, `--password` and `--no-shell-env`.

```sh
shipdeck ./scripts/deploy --key ~/.ssh/id_ed25519
shipdeck ./scripts/deploy                 # asks for the password in the screen
shipdeck --schema > deploy.schema.json    # the JSON Schema, for offline editors
```

## Arguments

### DEPLOY_ROOT

The folder whose subfolders each hold a `deploy.yaml`. Each direct subfolder with a `deploy.yaml` (or `deploy.yml`) is one deployable. The search is not recursive. See [Deploy root](/docs/guides/deploy-root).

| | |
| --- | --- |
| Value | a path to a folder |
| Required | yes, unless `--schema` is given |
| Error | `Error: <path> is not a folder` when the path is missing or a file |

The header of the screen shows the root as you typed it: `root ./scripts/deploy`.

## Options

### `--key <PATH>`

Log in with this private key file, and only this key.

| | |
| --- | --- |
| Value | a path to a private key file |
| Default | none: the `IdentityFile` of the host's `~/.ssh/config` entry, then a password prompt |
| Conflicts with | `--key-text`, `--password` |
| Error | `Error: the key file <path> does not exist` |

shipdeck expands a leading `~` itself, so `--key=~/.ssh/id_ed25519` also works in zsh, where the shell does not expand it after `=`. If the key is encrypted, the screen asks for its passphrase. If the server refuses the key, the deploy stops with `<host> refused the key <path> for user <user>`; there is no fallback to a password.

```sh
shipdeck ./scripts/deploy --key ~/.ssh/id_deploy
```

### `--key-text <TEXT>`

Log in with this private key's text, such as a CI secret.

| | |
| --- | --- |
| Value | the key file's text, line breaks included |
| Default | `SHIPDECK_SSH_KEY`, if it is set and not empty |
| Conflicts with | `--key`, `--password` |

The text shows in `ps` while shipdeck runs; `SHIPDECK_SSH_KEY` does not, so prefer the variable in CI. An encrypted key takes its passphrase from `SHIPDECK_KEY_PASSPHRASE`, or the screen asks for it. If the server refuses the key, the deploy stops with `<host> refused the key text for user <user>`.

```sh
SHIPDECK_SSH_KEY="$DEPLOY_KEY" shipdeck deploy ./scripts/deploy my-api   # DEPLOY_KEY: a CI secret
```

### `--password <PASSWORD>`

Log in with this password.

| | |
| --- | --- |
| Value | the password, as text |
| Default | `SHIPDECK_PASSWORD`, if it is set and not empty |
| Conflicts with | `--key`, `--key-text` |

The password lands in your shell history; `SHIPDECK_PASSWORD` does not. In zsh with `HIST_IGNORE_SPACE` set, start the command with a space to keep it out:

```sh
 shipdeck ./scripts/deploy --password 's3cret'
```

If the server refuses it, the deploy stops with `<host> refused the password for user <user>`.

The first login found wins, for every server of the run: `--key`, `--key-text`, `--password`, `SHIPDECK_SSH_KEY`, `SHIPDECK_PASSWORD`. With none of them, shipdeck logs in the way `ssh` does: the key named by `IdentityFile` for the host in `~/.ssh/config` first, then, if there is none or it is refused, a password prompt in the screen. See [SSH and login](/docs/guides/ssh).

| Flags | Header shows |
| --- | --- |
| `--key P` | `login key P` |
| `--key-text T` or `SHIPDECK_SSH_KEY` | `login key text` |
| `--password X` or `SHIPDECK_PASSWORD` | `login password` |
| none | `login ~/.ssh/config key, else a password` |

### `--no-shell-env`

Run server commands without the login shell's startup files, on every server of the run.

| | |
| --- | --- |
| Default | off: each connection loads what `~/.bashrc`, `~/.zshrc` and the like export (nvm, pyenv, a longer `PATH`) |
| Per server | `ssh.shell_env: false` in its `deploy.yaml` |

Loading the startup files costs a second or two per connection. Turn it off when a startup file expects a person (it starts tmux or asks a question), or when server commands should see the plain SSH environment; then name tools by absolute path or install them system-wide.

### `--schema`

Print the JSON Schema of `deploy.yaml` to stdout and exit with `0`. It runs before anything else, so a deploy root given with it is ignored. Use it for editor completion when you work offline:

```sh
shipdeck --schema > deploy.schema.json
```

The output starts with `"$id": "https://raw.githubusercontent.com/Naz-Ovh/shipdeck/v<version>/deploy.schema.json"`, the version you run.

### `-h`, `--help`

Print the help and exit:

```txt
Build locally, deploy over SSH as a systemd service or PM2 app, roll back any release.

Usage: shipdeck [OPTIONS] [DEPLOY_ROOT]
       shipdeck <COMMAND>

Commands:
  init      Create a deployable folder with a deploy.yaml from a preset; asks for what the flags leave out
  deploy    Build and deploy one or more deployables, one after another, without the TUI
  rollback  Switch a deployable to a release already on the server, without the TUI
  releases  List the releases on the server, newest first
  man       The manual, for people and coding agents: `man index` (topics), `man configs` (deploy.yaml), `man details <KEY>...`
  help      Print this message or the help of the given subcommand(s)

Arguments:
  [DEPLOY_ROOT]  Folder whose subfolders each hold a deploy.yaml

Options:
      --key <PATH>           Log in with this private key file
      --key-text <TEXT>      Log in with this private key's text (it shows in `ps`; SHIPDECK_SSH_KEY does not)
      --password <PASSWORD>  Log in with this password (it lands in your shell history; SHIPDECK_PASSWORD does not)
      --no-shell-env         Run server commands without the login shell's startup files (~/.bashrc, ~/.zshrc, ...), on every server
      --schema               Print the JSON Schema of deploy.yaml, for editor completion
  -h, --help                 Print help
  -V, --version              Print version

Each folder under DEPLOY_ROOT with a deploy.yaml is one deployable.
Login, first found: --key, --key-text, --password, SHIPDECK_SSH_KEY,
SHIPDECK_PASSWORD; else the host's ~/.ssh/config key, then the TUI asks
for the password. SHIPDECK_KEY_PASSPHRASE unlocks an encrypted key.
deploy, rollback and releases run without the TUI and ask nothing.
init creates a deployable folder; it asks for what its flags leave out.
man is the full manual: `shipdeck man index`, `man configs`, `man details <KEY>...`.
```

`shipdeck help deploy` (or `shipdeck deploy --help`) shows each command's own flags.

The help shows `[DEPLOY_ROOT]` in brackets because it is optional when `--schema` or a command is given.

### `-V`, `--version`

Print `shipdeck <version>`, such as `shipdeck 0.6.1`, and exit.

## Errors before the screen opens

These are printed to the terminal and shipdeck exits without opening the screen.

| Situation | Output | Exit code |
| --- | --- | --- |
| No deploy root | `error: the following required arguments were not provided:` followed by `<DEPLOY_ROOT>` and the usage line | `2` |
| `--key` and `--password` together | `error: the argument '--key <PATH>' cannot be used with '--password <PASSWORD>'` | `2` |
| Root is not a folder | `Error: /nonexistent is not a folder` | `1` |
| Key file missing | `Error: the key file /nope/key does not exist` | `1` |
| A `deploy.yaml` has problems | the problem report on stderr (below) | `1` |

### The problem report

shipdeck reads and checks every `deploy.yaml` before it opens the screen. If any file has a problem, it prints a report to stderr and exits with `1`. For `shipdeck ./scripts/deploy` where `scripts/deploy/my-api-prod/deploy.yaml` holds only `name: x`:

```txt
✘ shipdeck did not start: 1 deploy.yaml file has 2 problems

my-api-prod/deploy.yaml
  error: `ssh` is missing
    ┌─ ./scripts/deploy/my-api-prod/deploy.yaml
    │
    = help: add `ssh: { host: my-server, user: deploy }`

  error: `service` is missing
    ┌─ ./scripts/deploy/my-api-prod/deploy.yaml
    │
    = help: add `service: { name: my-api, dir: /opt/my-api }`
```

Each file starts with a heading of its folder and file name. The path after `┌─` is the deploy root as you typed it plus the file; an absolute root under the current folder is shown relative to it. The report is in colour only when stderr is a terminal and `NO_COLOR` is not set. `NO_COLOR` affects only this report; the screen itself always uses its colours. Every message is listed in [Config problems](/docs/reference/config-problems).

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Normal quit, or `--schema`, `--help`, `--version`; for a command, the release is live |
| `1` | Bad deploy root, missing key file, problems in a `deploy.yaml`, or a terminal error; for a command, also an unknown name or a failure before the live release changed |
| `2` | Wrong usage: a missing argument or conflicting flags, or a key `man details` does not know |
| `3` | A command only: the new release failed and the previous one is live again |
| `4` | A command only: the new release failed and stays live (`--on-failure keep`) |
| `5` | A command only: the new release failed and putting the old one back failed too |
| `6` | `deploy` only: nothing changed since the live release, so nothing was deployed (`--allow-unchanged` deploys anyway) |
| `130` | A command only: stopped with Ctrl-C twice |

Scripts rely on these numbers: new outcomes get new codes, and none is ever renumbered.

A deploy or rollback that fails inside the screen does not change the exit code: quitting the screen exits with `0` whatever happened. You see the result on the [Operation screen](/docs/reference/screens#operation). The commands report it in the exit code instead.

## Start a deployable

### `init <DEPLOY_ROOT> [NAME]`

Creates `<DEPLOY_ROOT>/<NAME>/` with a `deploy.yaml` written from a preset, an empty `.env` and a `.gitignore` that keeps `.env` out of git. It connects to nothing. In a terminal it asks for whatever the flags leave out (Esc stops without writing anything). With no terminal it asks nothing, and `NAME`, `--preset` and `--host` are required.

```sh
shipdeck init ./scripts/deploy
shipdeck init ./scripts/deploy my-api --preset nodejs --manager pm2 --host prod
```

```txt
? Name: my-api
? Preset:
  nodejs  built here; the server installs production dependencies
  golang  one static binary, nothing to install on the server
  java    built with Gradle; the server needs Java
  kotlin  built with Gradle; the server needs Java
> rust    one binary, nothing to install on the server
  dart    compiled to one executable, nothing to install on the server
  python  the source ships; the server builds its virtualenv
  bun     compiled to one executable, nothing to install on the server
```

| Flag | When left out |
| --- | --- |
| `NAME` | Asked. The folder's name, also `name` and `service.name`. `service.dir` is `/opt/<NAME>`. |
| `--preset <PRESET>` | Asked. `nodejs`, `golang`, `java`, `kotlin`, `rust`, `dart`, `python` or `bun`. |
| `--manager <systemd\|pm2>` | Asked, else `systemd`. |
| `--host <HOST>` | Asked. An address or an alias from `~/.ssh/config`. |
| `--user <USER>` | Asked, offering the alias's `User`; else the alias's `User`. |
| `--project <PATH>` | Asked, else the current folder. Written relative to the new folder. |

What `init` writes passes the same checks as a launch; a problem is printed the [same way](#the-problem-report) and nothing is written. It never replaces an existing `deploy.yaml`, and it leaves an existing `.env` or `.gitignore` alone. The presets are a starting point: check the build command and paths against your project.

## Without the UI

Three commands run the same deploy, rollback and release list as the screen, for scripts and CI. They take the deploy root first, then a deployable by its folder name or its `name`. Every `deploy.yaml` under the root is checked first, as for the screen. Progress goes to stderr as plain lines, in colour only when stderr is a terminal and `NO_COLOR` is not set. Nothing waits for an answer.

### `deploy <DEPLOY_ROOT> <NAME>...`

Builds and deploys each deployable in turn. The first that does not succeed stops the rest, and the ones left are listed as `▲ not deployed: ...`.

```sh
shipdeck deploy ./scripts/deploy my-api --key ~/.ssh/id_deploy
```

```txt
━━ My API (prod) · deploy → deploy@203.0.113.10:/opt/my-api
━━ Preflight: checking your PC and the server
› connect deploy@203.0.113.10 (key /home/me/.ssh/id_deploy)
⋮
✔ My API (prod): v0.3.1-ab12cd3-20261014.153012 is live (1m12s)
```

Each step prints once, when it ends; a long step also prints its progress every 5 seconds. The last line says what is live now.

#### `--on-failure <rollback|keep>`

What to do when the new release fails after the switch: at the switch, the restart or the health check. It overrides [`pipeline.failed.rollback`](/docs/guides/health-and-rollback) for this run.

| Value | Effect |
| --- | --- |
| `rollback` (default) | Put the release that was live back at once. Exit code `3`. |
| `keep` | Keep the failed release live, to look at it. Exit code `4`. Roll back later with `shipdeck rollback`. |

#### `--allow-unchanged`

Deploy even when nothing changed since the live release: the new release's fingerprint (its files, modes, links, service file and `deploy.yaml`) equals the live one's. Without it such a deploy stops at Pack, before anything on the server changes, with exit code `6`:

```txt
▲ My API (prod): nothing changed since v0.3.1-ab12cd3-20261014.153012, so nothing was deployed; --allow-unchanged deploys it anyway
```

With several deployables, an unchanged one stops the rest like any other result but success.

### `rollback <DEPLOY_ROOT> <NAME> --to <RELEASE>`

Makes a release already on the server live again. A release kept only as its backup is unpacked first and set up again with `pipeline.setup`; an old `.tar.gz` is unpacked first. `RELEASE` is an id as `shipdeck releases` lists it. A rollback whose health check fails puts back what was live. See [Releases](/docs/guides/releases#rolling-back-by-hand).

```sh
shipdeck rollback ./scripts/deploy my-api --to v0.3.0-9f8e7d6-20261012.091000
```

### `releases <DEPLOY_ROOT> <NAME>`

Prints the releases on the server to stdout, newest first, as aligned columns. `STATE` is `live`, `unpacked`, `compressed` (only its backup, or an old `.tar.gz`, is in `backups/`) or `not-ours` (a folder shipdeck did not create, which it never switches to).

```txt
RELEASE                         VERSION  COMMIT   BUILT (UTC)       SIZE      STATE       DEPLOYED BY
v0.3.1-ab12cd3-20261014.153012  0.3.1    ab12cd3  2026-10-14 15:30  31.0 MiB  live        me@laptop
v0.3.0-9f8e7d6-20261012.091000  0.3.0    9f8e7d6  2026-10-12 09:10  31.0 MiB  unpacked    me@laptop
```

### What the screen would ask

| The screen asks | The commands |
| --- | --- |
| Deploy this? | Running the command is the yes. |
| Roll back? | `--on-failure`. |
| Nothing changed: deploy anyway? | No, unless `--allow-unchanged`. |
| Trust a server seen for the first time? | No, and the command stops with the key's fingerprint. `--trust-new-host` trusts it and saves it to `~/.ssh/known_hosts`. A changed key is always refused. |
| A password or a key passphrase? | Never asked; the login fails with a hint. Use `--key` or `SHIPDECK_SSH_KEY` (with `SHIPDECK_KEY_PASSPHRASE` for an encrypted key), or `SHIPDECK_PASSWORD`. |

The first Ctrl-C only warns, since stopping can leave the server between two releases; a second one stops at once with exit code `130`.

## The manual

### `man [index | configs | details <KEY>...]`

The whole manual, built into the binary, for you and for the coding agent helping you. It matches the version you run, needs no network and reads no file.

| Command | Prints |
| --- | --- |
| `shipdeck man` or `man index` | every topic as `key: brief`, by section |
| `shipdeck man configs` | every `deploy.yaml` property as a YAML tree, with its type, default and brief |
| `shipdeck man details <KEY>...` | topics and properties in full |

A key is a topic key from the index (`quickstart`, `step.health`, `exit-codes`) or a property path from `man configs` (`service.env`, `pipeline.health.url`). Give several, apart or comma-separated:

```sh
shipdeck man details agents cli.deploy
shipdeck man details "agents, cli.deploy, service.start"
```

Each result is its own block, in the order asked, so an agent can tell them apart:

```txt
<topic key="step.health" brief="...">
the page
see: related keys
</topic>
<config key="service.env" type="map of text, default {}" brief="...">
the details
see: related keys
</config>
For more, check out https://forgedoc.naz.ovh/llms.txt
```

A key it does not know prints nothing on stdout: stderr names it with the closest keys, and the exit code is `2`.
