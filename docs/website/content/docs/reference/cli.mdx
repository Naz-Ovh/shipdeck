Run `shipdeck` in the folder that holds your root file and it opens the terminal UI. For
scripts and CI, `deploy`, `rollback`, `releases`, `server-info`, `work`, `events`, `setup`
and `tree` do the same work [without the UI](#without-the-ui), and `man` prints
[the manual](#the-manual).

## Synopsis

```txt
shipdeck [-C <DIR>] [-c <FILE>] [-E <FILE>] [LOGIN] [SERVER]
shipdeck init     [NAME] [--preset <PRESET>] [--manager systemd|pm2] [--host <HOST>] [--user <USER>] [--project <PATH>]
shipdeck deploy   [DEPLOY]... [--on-failure rollback|keep] [--allow-unchanged]
shipdeck rollback <DEPLOY> <RELEASE>
shipdeck releases   [DEPLOY]
shipdeck server-info [DEPLOY]
shipdeck work     [DEPLOY] [--cleanup]
shipdeck events   [DEPLOY] [--after <N>] [--limit <N>]
shipdeck setup    [DEPLOY] [--access full|commands] [--sudo-password <VALUE>]
shipdeck tree     [DEPLOY] [--app <APP>] [--depth <N>] [--build] [--json]
shipdeck man      [index | configs | details <KEY>...]
shipdeck --schema
```

`[LOGIN]` is `--key-file`, `--key-text`, `--password`, `--no-shell-env`, `--trust-new-host`, and
on Windows `--gitshell-path`. `[SERVER]` is `-H`, `-P` and `-U`. Every server command takes them.

```sh
shipdeck --key-file ~/.ssh/id_ed25519                 # the TUI, in this folder
shipdeck deploy production --key-file ~/.ssh/id_ed25519
shipdeck deploy scripts/p.yaml                   # one deploy file, no root file
shipdeck -C apps/api deploy production           # as if started in apps/api
shipdeck -c ops/root.yaml deploy staging         # another root file
shipdeck --schema > deploy.schema.json           # the JSON Schema, for offline editors
```

## Choosing what to read

Shipdeck reads the root file in the project folder: `shipdeck.yaml` or `.shipdeck`.

- `shipdeck` opens the TUI on every deploy the root file lists, including deploys written in
  place.
- `shipdeck deploy production` reads the root file, then that deploy.
- `shipdeck` with no root file stops and names the file it expected.
- `-C <DIR>` moves the project folder, as `git -C` does; every relative path starts there.
- `-c <FILE>` reads another root file. It does not change the project folder.

A deploy file named as a `DEPLOY` argument needs no root file at all.

## `DEPLOY`

A `DEPLOY` argument is one of two things, and only the ending decides:

- a name, such as `production`: a key under `deploys:` in the root file;
- a file ending in `.yaml` or `.yml`: that deploy file, on its own.

Anything else, such as `./production`, is an error. Without an argument:

- `deploy` uses the only deploy of the root file, and refuses when there are several;
- `releases`, `server-info`, `work`, `events`, `setup` and `tree` do the same;
- with a deploy file named, the one deploy in that file is used.

`rollback` always needs the deploy, because it takes two arguments.

## Options

### `-C, --cwd <DIR>`

| | |
| --- | --- |
| Value | a folder |
| Default | the folder shipdeck was started in |
| Error | `<DIR> is not a folder` |

It applies first: every relative path on the command line, including `-c` and a deploy file
argument, starts from it.

### `-c, --config <FILE>`

| | |
| --- | --- |
| Value | a file: a root file, or one named `.shipdeck` |
| Default | none: `shipdeck.yaml` or `.shipdeck` in the project folder |
| Error | `<FILE> is a deploy file, not a root file`, with the command to run instead |

It reads another root file and leaves the project folder alone. The file must hold `root: true`.

### `-E, --env-file <FILE>`

| | |
| --- | --- |
| Value | a file of `NAME=value` lines |
| Default | `.env` in the project folder, when it exists |
| Error | `the env file <path> does not exist`, when you named it |

A relative path starts from the project folder, as for `-c`. Only one file is read. Its values
are for shipdeck only: `${NAME}` in the deploy file, `SHIPDECK_SSH_*`, and the login variables.
Your commands never see them. A variable in the real environment wins over the file. See
[Server details outside the file](/docs/guides/ssh#server-details-outside-the-file).

### `-H, --host <HOST>`, `-P, --port <PORT>`, `-U, --user <USER>`

| | |
| --- | --- |
| Value | a host or alias, a port from 1 to 65535, a user name |
| Default | none: `SHIPDECK_SSH_HOST`, `SHIPDECK_SSH_PORT`, `SHIPDECK_SSH_USER`, then the file |
| Error | with more than one deploy: the option names what is set and points to `~/.ssh/config` aliases and `${NAME}` |

They replace `server.ssh.host`, `port` and `user` for a run with exactly one deploy. The output
says where a value came from, for example `host from --host`.

### `--key-file <PATH>`

Log in with this private key file, and only this key.

| | |
| --- | --- |
| Value | a path to a private key file |
| Default | none: the `IdentityFile` of the host's `~/.ssh/config` entry, then a password prompt (the TUI only) |
| Conflicts with | `--key-text`, `--password` |
| Error | `Error: the key file <path> does not exist` |

shipdeck expands a leading `~` itself, so `--key-file=~/.ssh/id_ed25519` also works in zsh. If the
key is encrypted, the TUI asks for its passphrase, or `SHIPDECK_KEY_PASSPHRASE` answers it.

### `--key-text <TEXT>`

Log in with this private key's text, such as a CI secret. It shows in `ps`; `SHIPDECK_SSH_KEY`
does not. It has no short form.

### `--password <PASSWORD>`

Log in with this password. It lands in shell history; `SHIPDECK_PASSWORD` does not. It has no
short form, for that reason.

The order all four are tried in is on [Login](/docs/guides/ssh).

### `--no-shell-env`

Run server commands without the login shell's startup files, for every server in this run.
It overrides each deploy file's `server.ssh.shell_env`. See [SSH and login](/docs/guides/ssh).

### `--trust-new-host`

Record a server's key in `~/.ssh/known_hosts` the first time it is seen, instead of asking.
A changed key for a known host is still refused. See [SSH and login](/docs/guides/ssh).

### `--gitshell-path <PATH>` (Windows)

Run local commands with this `sh.exe` instead of the one Git for Windows has. Also reads
`SHIPDECK_GITSHELL_PATH`.

## `init`

Writes a root file, a deploy file, an empty `.env` and a `.gitignore` in the current
folder. It asks for what the flags leave out when there is a terminal; without one, `NAME`,
`--preset` and `--host` are required.

| Flag | Value | Default |
| --- | --- | --- |
| `NAME` | the deploy name and the default process name | asked |
| `--preset` | `nodejs`, `golang`, `java`, `kotlin`, `rust`, `dart`, `python`, `bun` | asked |
| `--manager` | `systemd` or `pm2` | asked, or `systemd` |
| `--host` | an address, or a `~/.ssh/config` alias | asked |
| `--user` | the SSH user | the alias's `User` |
| `--project` | your source folder | the current folder |

The file it writes is checked as a launch would check it, so init never writes a config
shipdeck would refuse. An existing root file is never replaced.

## Without the UI

### `deploy [DEPLOY]...`

Builds and deploys each in turn; the first non-zero exit stops the rest, and the ones not run
are named. It prints one line per step as it ends and the outcome at the end.

| Flag | Meaning |
| --- | --- |
| `--on-failure rollback` | roll back at once after a failure in switch, restart, nginx or health |
| `--on-failure keep` | never roll back on its own; the failed release stays live |
| `--allow-unchanged` | deploy even when the release holds what the live one does |

`--on-failure` maps onto `release.steps.rollback.mode` and wins over the file, but only when
it is given: `rollback` is `auto`, `keep` is `off`. Without it, the file decides, so
`mode: off` keeps the failed release live. The flag cannot choose `ask`, so a headless run
never waits for an answer; `ask` with nobody to answer rolls back after `ask_secs`.

### `rollback <DEPLOY> <RELEASE>`

Makes an older release live again. The release id is exactly what `releases` prints. A
release kept only as its backup is unpacked and its `setup.server` runs again.

A release from before config format 2 has no `.shipdeck/settings.json`, so the rollback is
refused: `this release was made before config format 2; deploy again`.

### `releases [DEPLOY]`

Lists what is on the server, newest first, to stdout:

```txt
release                              kind        current  backup     size
v1.4.0-ab12cd3-20261110.120000       open        yes      yes        12.4 MiB
v1.3.9-def5678-20261108.090000       open                 yes         5.1 MiB
v1.3.8-0a1b2c3-20261101.170000       compressed  -        yes         2.2 MiB
```

`kind` is `open` (unpacked, ready to switch to) or `compressed` (only its backup). It reads
only; nothing on the server changes.

### `server-info [DEPLOY]`

Prints Linux and kernel, CPU and cores, memory, disk at the deploy folder, uptime, the agent
version, and the tools shipdeck looked for.

### `work [DEPLOY] [--cleanup]`

Shows the live release, the service state, unfinished files, an activation that was never
confirmed, and the newest saved events. `--cleanup` is the approval to remove the unfinished
files; it removes only the paths this command just listed.

### `events [DEPLOY] [--after N] [--limit M]`

Prints the numbered events the server saved, oldest first: `#sequence time operation kind
detail`. `--after` follows on from the last sequence you saw; one page is at most 1000.

### `setup [DEPLOY] [--access full|commands] [--sudo-password PASSWORD]`

Prepares a server once: the packages, the deploy folder, and the sudo rule.
`--access commands` grants password-free sudo for exactly what shipdeck runs (the default
when nobody can be asked); `--access full` for everything. The sudo password travels on
stdin and is never saved; `SHIPDECK_SUDO_PASSWORD` keeps it out of history.

### `tree [DEPLOY]`

Prints every path the next release will hold, from local files only. It never connects to
the server, and it uses the same code as `deploy`, so the two always agree.

| Flag | Meaning |
| --- | --- |
| `--app <APP>` | only that app's folder |
| `--depth <N>` | fold folders deeper than `N` into `name/ (<count> files)` |
| `--build` | run the `build` steps first, so build output is there |
| `--json` | one object per path: `path`, `kind`, `from`, `local`, `mode`, `size` |

When a pattern matches nothing, it prints the tree it could and the missing patterns, then
exits with 1.

## The manual

`shipdeck man index`, `shipdeck man configs`, and `shipdeck man details <KEY>...` print the
manual built into the binary. It needs no file and no network.

## `--schema`

Prints the JSON Schema of the root file and the deploy file to stdout. The same file is
published at each release for editor completion. See
[Config](/docs/reference/config#editor-completion).

## Exit codes

Scripts depend on these: they are added to, never renumbered.

| Code | Meaning |
| --- | --- |
| `0` | success: the release is live |
| `1` | failed before anything live changed; a config or connection problem; or a refused operation, including another operation already running on the project |
| `2` | the command line was wrong; nothing ran |
| `3` | the new release failed after the switch and the previous one is live again |
| `4` | the new release failed after the switch and was kept live, as you chose |
| `5` | the new release failed and putting the previous one back failed too; inspect the server |
| `6` | nothing changed since the live release; nothing was deployed |
| `130` | interrupted with Ctrl-C twice |

## What it prints

`deploy` and `rollback` write to stderr: one heading per deploy, one line per step as it
ends, the step's commands and output, and the outcome. `releases` and `tree` write their tree
or table to stdout, so `shipdeck tree production --json` pipes into `jq`.

A config problem is printed as the block shown in
[Config problems](/docs/reference/config-problems) and nothing is attempted.
