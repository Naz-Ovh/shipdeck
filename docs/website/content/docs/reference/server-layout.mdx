shipdeck keeps everything for one deploy under `dir`, plus one systemd unit per process in
`/etc/systemd/system/`. The examples use `dir: /opt/shop` and the app `api`.

<Callout title="A stable contract">
shipdeck treats this layout and the release id format as a contract with servers it has
already deployed to. They change only on purpose, so your own scripts and backups can rely
on them.
</Callout>

`shipdeck tree` prints the paths of the next release before it is made.

## Release ids

```txt
v<version>-<git commit>[-dirty]-<UTC date.time>
```

| Part | From |
| --- | --- |
| `<version>` | `release.steps.build.version_from`, else the first of `Cargo.toml`, `package.json`, `pyproject.toml`, `VERSION` in the project folder, else the latest git tag, else `0.0.0` |
| `<git commit>` | `git rev-parse --short=7 HEAD`, or `nogit` outside a repository |
| `-dirty` | tracked files had uncommitted changes at build time |
| `<UTC date.time>` | the build time, `%Y%m%d.%H%M%S` |

Ids sort by the build time, never by text, so `v0.10.0` counts as newer than `v0.9.0`.
`shipdeck` only treats an id it could have made as a release: a folder whose name does not
fit is listed as `not ours` and never touched.

## `.shipdeck/`

| File | Written when |
| --- | --- |
| `release.json` | always: the id, version, commit, dirty flag, build time and who deployed |
| `settings.json` | always: the resolved deploy, with placeholders unresolved |
| `<process>.service` | a systemd app |
| `<process>.pm2.json` | a PM2 app without its own ecosystem file |
| `oxfile.toml` | any oxmgr app. Not written yet: such a deploy stops at preflight |
| `nginx/<name>-<app>.conf` | any app with `nginx:`. Not written yet, for the same reason |

A rollback reads the restored release's `settings.json` for its `setup.server`,
`health.server` and `done` commands, then resolves the placeholders with that release's
values. That is why a release from before config format 2 is refused.

## Ownership and modes

- The agent may run as root, but new files and folders under `dir` are given back to the SSH
  user. With a non-root user, everything there belongs to that user.
- Modes come from your PC: folders `0755`, a binary `0755`, `.shipdeck/` files `0644`, files
  whose name starts with `.env` `0600`, other files keep their local mode (`0644` from
  Windows, which has no Unix modes). A file copied from the live release gets the mode the
  new release has for it. Symlinks stay symlinks.
- If shipdeck created `dir` with `sudo -n mkdir` on a first deploy, it hands it to the SSH
  user with `chown`.
- The process runs as `systemd.user`, by default the SSH user. That user must be able to read
  the release.

<Callout type="warn" title="A different systemd.user">
Release files belong to the SSH user and `.env` files are `0600`. systemd still reads
`env_file` for the process, but a `systemd.user` other than the SSH user cannot open `.env`
itself, and may not be able to write to `shared/`.
</Callout>

## Outside dir

| Path | Written by | Content |
| --- | --- | --- |
| `/etc/systemd/system/<process>.service` | `sudo -n install -m 0644` (no sudo as root), at every switch | A copy of `current/.shipdeck/<process>.service`. It refers only to paths under `current/`. |

The unit is always installed from the same path, `<dir>/current/.shipdeck/<process>.service`,
so every deploy finds it in the same place. Before config format 2 it was
`<dir>/current/<process>.service`; a deploy now installs it from the new path by itself.

`shipdeck server-info` lists the processes, and `shipdeck releases` lists the releases.
