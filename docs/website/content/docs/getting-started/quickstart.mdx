---
title: Quickstart
description: Install Shipdeck, write a project file and a deploy file, deploy, and inspect or roll back a release.
---

Shipdeck builds locally, stages a checked release over SSH, then switches the live folder
and restarts your processes. This page uses a Rust service called `my-api`. You need its
source, a Linux server with systemd, and an existing SSH user.

## 1. Install and connect

```sh
curl -LsSf https://shipdeck.naz.ovh/install.sh | sh
shipdeck --version
```

Add your real server address, existing user, and private key to your SSH config:

```ini
Host prod
  HostName 203.0.113.10
  User deploy
  IdentityFile ~/.ssh/id_ed25519
```

Shipdeck reads this alias. It uses the named key; it does not use ssh-agent or try unnamed
default keys. Review the server fingerprint when first connecting. CLI commands need
`--trust-new-host` for a new key.

## 2. Prepare the server

Once per server, either run the setup script as root (see
[Server access](/docs/guides/server-access)) or, from your PC:

```sh
shipdeck setup production
```

## 3. Create the deployment

From your app repository root:

```sh
shipdeck init my-api --preset rust --manager systemd --host prod
```

This writes four files in the current folder: `shipdeck.yaml` (the project file),
`deploy.yaml` (the deploy file), an empty `.env`, and a `.gitignore` that keeps the `.env`
out of git. Edit `deploy.yaml`:

```yaml
name: my-api
server:
  ssh: { host: prod, user: deploy }
  dir: /opt/my-api

apps:
  my-api:
    source: .
    files: [.env]
    binary: target/release/my-api
    process:
      systemd: {}
    steps:
      health:
        url: http://127.0.0.1:8080/health

release:
  steps:
    build:
      local: cargo build --release
```

Replace the binary name and health URL with your app's values. Fill in the `.env`; do not
commit secrets.

This build command assumes your computer builds a binary compatible with the server's Linux,
CPU, and libc. On macOS, Windows, or a different CPU, use a Linux cross-build and change
`binary` to its output. Shipdeck checks compatibility after building; it does not
cross-compile for you.

For Node.js, Go, Python, or another stack, choose a matching preset or
[example](/docs/guides/examples). Use `process.pm2` for PM2. Several apps can share one
release through the [deploy file](/docs/monorepos).

## 4. Check what will ship

```sh
shipdeck tree production
```

It prints every path the next release will hold, using the same code as a deploy, and needs
no connection.

## 5. Deploy and check

```sh
shipdeck
```

The TUI lists the deploys of your project file. Select **my-api**, press Enter, and confirm.
Shipdeck validates the config, builds locally, transfers and checks files, runs setup, saves
a backup, switches `current`, restarts, and checks health. The old release remains live
during preparation; your custom commands can still have outside effects.

For scripts and CI:

```sh
shipdeck deploy production --on-failure rollback
```

The command asks no questions. Supply login details and review any new host fingerprint
before using `--trust-new-host`. Exit `0` means success; `6` means nothing changed. See
[exit codes](/docs/reference/cli#exit-codes) for other results.

## 6. Inspect or roll back

In the UI, `r` opens releases. `D` inspects files. Select an older release and press Enter to
roll back; you need at least two releases first. `:logs` follows logs; `:restart`, `:stop`,
and `:start` control the processes. `q` quits.

The first connection prepares a root-owned server agent under `/opt/shipdeck/agent`; it runs
over SSH and exits on disconnect. After an interrupted operation, reconnect and inspect
before retrying:

```sh
shipdeck work production
shipdeck events production --after 0
```

Unfinished files stay for inspection. Add `--cleanup` to `work` only when you intend to
remove them. A dropped connection during activation leaves an uncertain result; inspect the
live release and processes.

Rollback restores files and the restored release's own setup state. A release kept only as a
backup has its setup run again. It does not reverse database migrations or custom side
effects.

For focused help: `shipdeck man index`, then
`shipdeck man details cli.deploy process.start`.
