---
title: Quickstart
description: Install Shipdeck, write one config, deploy, and inspect or roll back a release.
---

Shipdeck builds locally, stages a checked release over SSH, then switches the
live folder and restarts your service. This page uses a Rust service called
`my-api`. You need its source, a Linux server with systemd, and an existing SSH
user. Reading takes under five minutes; setup and build time vary.

## 1. Install and connect

```sh
curl -LsSf https://shipdeck.naz.ovh/install.sh | sh
shipdeck --version
```

Add your real server address, existing user, and private key to your SSH config:

```ini
Host prod
  HostName 203.0.113.10
  User deploy
  IdentityFile ~/.ssh/id_ed25519
```

Shipdeck reads this alias. It uses the named key; it does not use ssh-agent or
automatically try unnamed default keys. Review the server fingerprint when first
connecting. CLI commands need explicit trust for a new key.

## 2. Create the deployment

From your app repository root:

```sh
shipdeck init ./scripts/deploy my-api --preset rust --manager systemd --host prod
```

This creates a deploy config, an empty `.env`, and a rule to keep that secret
file out of git. Edit `scripts/deploy/my-api/deploy.yaml`:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/Naz-Ovh/shipdeck/v0.7.1/docs/schema/deploy.schema.json
name: My API
project: ../../..

ssh:
  host: prod
  user: deploy

service:
  name: my-api
  dir: /opt/my-api
  start: ./my-api
  env_file: .env

pipeline:
  build:
    run:
      local: cargo build --release
  pack:
    binary: target/release/my-api
    files:
      include:
        deploy: [.env]
  health:
    url: http://127.0.0.1:8080/health
```

Replace the binary name, start command, and health URL with your app's values.
Fill in the deployment's `.env`; do not commit secrets.

This build command assumes your computer builds a binary compatible with the
server's Linux, CPU, and libc. On macOS, Windows, or a different CPU, use a
Linux cross-build and change `pack.binary` to its output. Shipdeck checks
compatibility after building; it does not cross-compile for you.

For Node.js, Go, Python, or another stack, choose a matching preset or
[example](/docs/guides/examples). Use `service.manager: pm2` for PM2.
Several apps can share one release through the [monorepo config](/docs/monorepos).

## 3. Deploy and check

```sh
shipdeck ./scripts/deploy
```

Select **My API**, press Enter, and confirm. Shipdeck validates the config,
builds locally, transfers and checks files, runs setup, saves a backup,
switches `current`, restarts, and checks health. The old release remains live
during preparation; your custom commands can still have outside effects.

For scripts and CI:

```sh
shipdeck deploy ./scripts/deploy my-api --on-failure rollback
```

The command asks no questions. Supply login details and review any new host
fingerprint before using `--trust-new-host`. Exit `0` means success;
`6` means nothing changed. See [exit codes](/docs/reference/cli#exit-codes)
for other results.

## 4. Inspect or roll back

In the UI, `r` opens releases. `D` inspects files.
Select an older release and press Enter to roll back; you need at least two
releases first. `:logs` follows logs; `:restart`, `:stop`, and `:start`
control services. `q` quits.

The first connection prepares a root-owned server agent under `/opt/shipdeck/agent`; it runs over SSH and exits on disconnect.
After an interrupted operation, reconnect and inspect before retrying:

```sh
shipdeck work ./scripts/deploy my-api
shipdeck events ./scripts/deploy my-api --after 0
```

Unfinished files stay for inspection. Add `--cleanup` to `work` only when you
intend to remove them. A dropped connection during activation leaves an
uncertain result; inspect the live release and services.

Rollback restores files and saved service settings. A compressed backup runs
setup again. It does not reverse database migrations or custom side effects.

For focused help: `shipdeck man index`, then
`shipdeck man details cli.deploy service.start`.
