shipdeck runs on Linux, Windows and macOS. Linux is the main platform, then Windows, then macOS. On Linux and macOS the quickest way in is the prebuilt binary; building from source with cargo works too. On Windows there is no prebuilt binary yet, so build it with cargo (see [On Windows](#on-windows)).

## Install the prebuilt binary

```sh
curl -LsSf https://shipdeck.naz.ovh/install.sh | sh
```

The script downloads the build for your machine, checks its SHA-256, and puts `shipdeck` in `~/.local/bin` (or `$XDG_BIN_HOME` if you set it). If that folder is not on your `PATH` yet, it adds it in `~/.profile` and tells you how to load it into the current shell. Set `SHIPDECK_NO_MODIFY_PATH=1` to leave `~/.profile` alone, or `SHIPDECK_INSTALL_DIR` to install somewhere else:

```sh
curl -LsSf https://shipdeck.naz.ovh/install.sh | SHIPDECK_INSTALL_DIR=/usr/local/bin sh
```

There are builds for x86_64 and arm64 on both Linux and macOS. On Linux the script picks one of two: the gnu build when the system has glibc 2.28 or newer, and a static musl build otherwise, for Alpine and older distributions. Both are the same program.

### Pin a prebuilt version

Without options the script installs the latest release. `-V` picks one from the [releases on GitHub](https://github.com/Naz-Ovh/shipdeck/releases) instead (the `v` is optional):

```sh
curl -LsSf https://shipdeck.naz.ovh/install.sh | sh -s -- -V=v0.3.1
```

To upgrade, run the install command again. `sh -s -- --help` lists the options.

### With cargo-binstall

If you use [cargo-binstall](https://github.com/cargo-bins/cargo-binstall), it installs the same prebuilt binary into cargo's bin folder, without compiling:

```sh
cargo binstall --git https://github.com/Naz-Ovh/shipdeck shipdeck
```

shipdeck is not on crates.io, so `--git` is needed: binstall reads the version from the repository and downloads that release's archive. It picks the build itself: gnu on Linux with glibc, musl on Alpine and other musl systems, and the build for your CPU on macOS.

To upgrade, run the same command again once a new release is out.

### With bin

[bin](https://github.com/marcosnils/bin) installs the latest release from GitHub and keeps track of it for `bin update`:

```sh
bin install github.com/Naz-Ovh/shipdeck
```

On Linux it asks which archive to use. Pick the `linux-gnu` one, unless the system is Alpine or another musl distribution, or its glibc is older than 2.28; then pick `linux-musl`.

To upgrade, run `bin update shipdeck`.

## Build with cargo

Every path from here on compiles shipdeck on your machine, so it needs a Rust toolchain and a C compiler (see [Requirements](#on-your-pc)). shipdeck is not on crates.io yet; cargo installs it from GitHub.

```sh
cargo install --git https://github.com/Naz-Ovh/shipdeck shipdeck
```

This builds the `shipdeck` binary and puts it in cargo's bin folder (usually `~/.cargo/bin`), which is on your `PATH` if you installed Rust with rustup.

### Pin a version

The repository has a tag per release (`v<version>`). To install exactly one of them, add cargo's `--tag` flag:

```sh
cargo install --git https://github.com/Naz-Ovh/shipdeck --tag v0.3.1 shipdeck
```

`--tag` is a plain cargo option, not something specific to shipdeck. Pinning is useful because two things name a version: the schema line at the top of your `deploy.yaml` files, and the `server-setup.sh` URL, which you pin to the tag of the shipdeck you run (see [Server access](/docs/guides/server-access)).

To upgrade later, run the same command with the new tag. Add `--force` if cargo says the binary is already installed.

## On Windows

There is no prebuilt Windows binary yet. Install from source with cargo, using Rust's MSVC toolchain (rustup's default on Windows):

```sh
cargo install --git https://github.com/Naz-Ovh/shipdeck shipdeck
```

[Git for Windows](https://gitforwindows.org) is required. Local commands (`run.local` and the build) run in its `sh.exe`, so one `deploy.yaml` works on every PC. shipdeck takes the first `sh.exe` of:

1. the one `--gitshell-path <PATH>` or the `SHIPDECK_GITSHELL_PATH` variable names;
2. the one `git var GIT_SHELL_PATH` names;
3. `sh.exe` in a folder on `PATH`;
4. `%ProgramFiles%\Git\usr\bin`, `%LOCALAPPDATA%\Programs\Git\usr\bin` and scoop's git.

A link to `sh.exe` works too, for example in `%LOCALAPPDATA%\Microsoft\WindowsApps`, which is on `PATH` by default. shipdeck follows the link and runs `sh.exe` from Git's folder, next to `cp`, `rm` and the rest.

A few things differ from Linux and macOS:

- **File modes.** Windows has no Unix modes, so every shipped file gets `0644`. `.env` files still get `0600` and `pipeline.pack.binary` `0755`, as on Linux. A script that must run on the server needs a `chmod +x` in `pipeline.setup.run.server`.
- **Line endings.** `deploy.yaml` must use LF. A carriage return anywhere is refused with `deploy.yaml has Windows line endings (CRLF); shipdeck reads LF only`. Save the file with LF; in Git, `*.yaml text eol=lf` in `.gitattributes` keeps it that way on Windows checkouts.
- **Paths.** Paths inside `deploy.yaml` always use `/`.
- **Links.** A symbolic link in the project has its `\` turned into `/`. A link to a drive or a root (`C:\app`, `\app`) is refused: it means nothing on the server.
- **`~/.ssh/config`.** `%u` in `IdentityFile` expands to `USERNAME` (`USER` elsewhere).

## Run from a clone

If you want to read the code or try a change, clone the repository and run it with cargo:

```sh
git clone https://github.com/Naz-Ovh/shipdeck
cd shipdeck
cargo run --release -p shipdeck -- ./path/to/deploy-root
```

Everything after `--` goes to shipdeck, so flags such as `--key` work the same way:

```sh
cargo run --release -p shipdeck -- ../my-app/scripts/deploy --key ~/.ssh/id_ed25519
```

## As a git submodule

You can keep shipdeck inside the project it deploys, pinned to a commit:

```sh
git submodule add https://github.com/Naz-Ovh/shipdeck scripts/shipdeck
git -C scripts/shipdeck checkout v0.3.1
```

Then either run it from there:

```sh
cd scripts/shipdeck
cargo run --release -p shipdeck -- ../deploy
```

or install the binary from the submodule with cargo's `--path` flag:

```sh
cargo install --path scripts/shipdeck/bin/shipdeck
```

People who clone your project later need `git clone --recurse-submodules`, or `git submodule update --init` after a plain clone.

## Requirements

### On your PC

The prebuilt binary needs only Linux or macOS, a modern terminal and, optionally, git. Building from source also needs a Rust toolchain and a C compiler. On Windows, Git for Windows is required too.

| Need | Why |
| --- | --- |
| A Rust toolchain, 1.89 or newer | To build shipdeck. The code uses the 2024 edition and let chains (stable since Rust 1.88), and the SSH library it uses, `russh` 0.64, declares 1.89 as its minimum. Install or update with [rustup](https://rustup.rs). |
| Linux, Windows or macOS | Local commands run through `sh -c`: the system's `sh` on Linux and macOS, Git for Windows' `sh.exe` on Windows (see [On Windows](#on-windows)). |
| A C compiler | The SSH library shipdeck uses pulls in a cryptography crate (`aws-lc-sys` 0.46) that compiles C code during the build. Most systems with a development toolchain (`build-essential` on Debian and Ubuntu, Xcode command line tools on macOS) already have one. In some setups its build uses CMake instead, so CMake may be needed too. If the build of `aws-lc-sys` fails, its error message says what is missing. |
| `git` (optional, except on Windows) | shipdeck reads the commit hash for the release name, marks releases built from uncommitted changes, falls back to the latest tag for the version, and uses your `user.name` as "deployed by". Without git the release name uses `nogit`. |
| Your build tools | Whatever your own build commands need: `cargo`, `cargo zigbuild`, `go`, `npm` and so on. |
| A modern terminal | shipdeck draws with 24-bit colour and Unicode box-drawing characters. |

### On the server

You install nothing of shipdeck's on the server. It needs:

- Linux with systemd and an SSH server.
- `sh`, which every Linux system has.
- `tar` and `zstd`, to unpack each release, and `sha256sum` (from `coreutils`), to check it. Most distributions ship `tar` and `coreutils`; if `zstd` is missing, preflight stops and says to install it (`apt install zstd`, or `dnf install zstd`).
- `curl` or `wget`, but only if you set `pipeline.health.url`.
- The root user, or a user with passwordless `sudo` for five specific commands. [Server access](/docs/guides/server-access) explains both, and the optional one-time setup script.
- At least 100 MiB of free disk space.

## Check the install

```sh
shipdeck --version
```

```txt
shipdeck 0.3.1
```

`shipdeck --help` lists the flags. The [Command line](/docs/reference/cli) reference covers each one.

## Editor completion

shipdeck generates a JSON Schema for `deploy.yaml` and publishes it with every release tag. Put this line at the top of a `deploy.yaml`, and any editor that uses the YAML language server (the VS Code YAML extension, Neovim, Zed, JetBrains IDEs) gives you completion, descriptions and errors as you type:

```yaml title="deploy.yaml"
# yaml-language-server: $schema=https://raw.githubusercontent.com/Naz-Ovh/shipdeck/v0.3.1/deploy.schema.json
```

The URL contains the version, so update it when you upgrade shipdeck. shipdeck itself ignores comments; the line is only for your editor.

To map the schema for every `deploy.yaml` in a repository at once, add this to `.vscode/settings.json` instead:

```json title=".vscode/settings.json"
{
  "yaml.schemas": {
    "https://raw.githubusercontent.com/Naz-Ovh/shipdeck/v0.3.1/deploy.schema.json": "**/deploy.yaml"
  }
}
```

To work offline, write the schema to a file and point your editor at it:

```sh
shipdeck --schema > deploy.schema.json
```
