Every message below is what shipdeck prints. The fix follows the message.

## Starting up

<Accordions>
  <Accordion title="✘ shipdeck did not read the deploy: 1 shipdeck file has 2 problems">
    A config file has a mistake. shipdeck reads every file it needs before it starts, and
    refuses to start at all if any has a problem. Each problem shows the file, line and column,
    a caret under the spot, and a `= help:` hint. See
    [Config problems](/docs/reference/config-problems).
  </Accordion>
  <Accordion title="there is no root file in <folder>; expected shipdeck.yaml or .shipdeck">
    shipdeck reads the root file in the project folder. Run it in that folder, name the folder
    with `-C <dir>`, or name a root file with `-c <file>`. A deploy file named as a `DEPLOY`
    argument needs no root file.
  </Accordion>
  <Accordion title="this folder has both shipdeck.yaml and .shipdeck">
    A folder holds one root file. Keep one of those two names. `shipdeck.yml` is not read at all.
  </Accordion>
  <Accordion title="unknown key `service`">
    Config format 2 has no `service`. A process is `apps.<app>.process`, with one of `systemd`,
    `pm2` or `oxmgr` inside. See [Upgrading](/docs/guides/upgrading#config-format-2) for every
    mapped key.
  </Accordion>
  <Accordion title="Error: the key file <path> does not exist">
    `--key-file` names a file that is not there. Check the path; shipdeck expands a leading `~`.
  </Accordion>
  <Accordion title="error: the argument '--key-file <PATH>' cannot be used with '--password <PASSWORD>'">
    Pass one login method. See [Login](/docs/guides/ssh).
  </Accordion>
  <Accordion title="No deploys yet">
    The root file has no `deploys:`, or the list is empty. Add one there, or name a deploy file
    as a `DEPLOY` argument.
  </Accordion>
</Accordions>

## Connecting

Connection problems show on the Deploys screen as a `✘` line under the deploy, and in the Log
panel when they happen during a deploy.

<Accordions>
  <Accordion title="Password prompts when shipdeck connects">
    shipdeck connects when you press `c` on a deploy, or when a deploy, the Releases screen or a
    rollback needs the server. With no key it asks once per `user@host` and keeps the answer in
    memory for this run only. To avoid the prompt, pass `--key-file` or add an `IdentityFile` to the
    alias. shipdeck does not use ssh-agent.
  </Accordion>
  <Accordion title="connecting to <user>@<host> timed out after 15s">
    The TCP connection did not open. Check the address, the port, and the server's firewall.
  </Accordion>
  <Accordion title="HOST KEY CHANGED for <host>: it differs from line <n> of ~/.ssh/known_hosts">
    The server shows a different key of the same type. Someone could be intercepting the
    connection. If the server was reinstalled, remove that line or run `ssh-keygen -R <host>`,
    then connect again.
  </Accordion>
  <Accordion title="the host key of <host> was not trusted">
    You refused the new key. Connect again and compare its fingerprint with
    `ssh-keygen -lf /etc/ssh/ssh_host_*_key.pub` on the server.
  </Accordion>
  <Accordion title="~/.ssh/config reaches <host> through `ProxyJump …`, which shipdeck cannot follow yet">
    Put the server's own address in `server.ssh.host`.
  </Accordion>
  <Accordion title="<host> refused the key <path> for user <user>">
    The server does not accept that key for that user. Add the public key to
    `~/.ssh/authorized_keys` on the server.
  </Accordion>
  <Accordion title="<user> may not run: sudo <command>">
    The sudo rule is missing or older than this shipdeck. Run `shipdeck setup`, or
    scripts/server-setup.sh as root on the server. See
    [Server access](/docs/guides/server-access).
  </Accordion>
</Accordions>

## The server

<Accordions>
  <Accordion title="the server has no zstd; install it (apt install zstd, or dnf install zstd)">
    Preflight names the package. `tar`, `zstd` and `sha256sum` are how releases are unpacked and
    checked.
  </Accordion>
  <Accordion title="<user> cannot create <dir>, and has no sudo without a password">
    The deploy folder does not exist and the user cannot make it. Run `shipdeck setup`, or create
    it by hand: `sudo install -d -o <user> <dir>`.
  </Accordion>
  <Accordion title="<user> cannot write to <dir>">
    The folder exists but belongs to someone else. Give it to the deploy user:
    `sudo chown -R <user> <dir>`.
  </Accordion>
  <Accordion title="<user> cannot find <tool> on the server">
    The program is not on the PATH the server commands see. Install it system-wide, or list it
    in `release.steps.preflight.requires` and fix the PATH. With a version manager, keep
    `server.ssh.shell_env` on.
  </Accordion>
  <Accordion title="<tool> is at /home/..., but the built-in unit hides home folders from the service (ProtectHome=true)">
    The built-in systemd unit sets `ProtectHome=true`. Install the runtime system-wide (for
    example in `/usr/bin`), use PM2, or write your own `process.systemd.template` without
    ProtectHome. See [systemd](/docs/man/systemd).
  </Accordion>
  <Accordion title="only <size> free on the server">
    A release needs room for the archive and the unpacked files. Free some space, or move
    `server.dir` to a bigger volume.
  </Accordion>
  <Accordion title="the server has <free> free; this release needs about <size>">
    Same as above, checked with the packed release's real size.
  </Accordion>
  <Accordion title="the systemd service <process> is still running and would clash with PM2">
    An older systemd unit still runs the app. Stop it: `sudo systemctl disable --now <process>`.
  </Accordion>
  <Accordion title="a deploy or rollback is already running">
    shipdeck runs one operation at a time per project. Wait for it, or inspect it with
    `shipdeck work`. A second operation is refused before anything changes.
  </Accordion>
</Accordions>

## Config and files

<Accordions>
  <Accordion title="these file patterns matched nothing: dist (not found)">
    A `files` entry found nothing. The build did not produce it, or the path is wrong. Run the
    build, or fix the path; `shipdeck tree` prints the same list without connecting.
  </Accordion>
  <Accordion title="<text> is outside the project folder, so it needs `to`">
    A `./`, `../` or absolute path in `release.files` has no place of its own. Give it one:
    `{ path: ./prod/config.json, to: config/prod.json }`.
  </Accordion>
  <Accordion title="<text> is outside the app's source, so it needs `to`">
    The same for an app file outside `apps.<app>.source`.
  </Accordion>
  <Accordion title="the binary target/release/api is a folder; `binary` names one file">
    `binary` takes one file. Point it at the file, or use `files` for a folder.
  </Accordion>
  <Accordion title="apps/api/api would hold two files: a generated file and ./other/api">
    A binary and a file land at the same path. Rename one, or give the binary a `to`.
  </Accordion>
  <Accordion title="the project folder <path> does not exist">
    The folder shipdeck runs in, or the one named by `-C`, is gone. Run it where the root file is.
  </Accordion>
  <Accordion title="app api: the source folder <path> does not exist">
    `apps.<app>.source` points at a folder that is not there. With `source: .` the app uses the
    project folder.
  </Accordion>
  <Accordion title="app api: the unit template <path> does not exist">
    `process.systemd.template` names a file on your PC. Fix the path, or remove the line to use
    the built-in unit.
  </Accordion>
  <Accordion title="nginx management is not built yet / oxmgr is not built yet">
    Both are parsed and checked, not built. Remove `nginx:` or the `oxmgr:` process for now.
  </Accordion>
  <Accordion title="1.4 is outside the project folder, so it needs `to`">
    A path in `release.files` that is not from the project folder needs a place. Give it `to`.
  </Accordion>
</Accordions>

## Build and upload

<Accordions>
  <Accordion title="the build failed: `<command>` exited with code <n>">
    A `build.local` command failed. Run it yourself in the project folder to see why.
  </Accordion>
  <Accordion title="the binary needs glibc <need>, but the server has <have>">
    Build against the server's glibc (for example `cargo zigbuild --target x86_64-unknown-linux-gnu.<have>`),
    or build a static musl binary.
  </Accordion>
  <Accordion title="the binary is built for <arch>, but the server is <arch>">
    Build for the server's CPU. Preflight compares the two before anything ships.
  </Accordion>
  <Accordion title="<path> changed while the release was packed">
    Something wrote to a shipped file during the deploy. Stop it (a watcher, a dev server), then
    deploy again.
  </Accordion>
  <Accordion title="Nothing changed since <release>, the live release">
    The release's content equals the live one. Nothing was deployed; exit code 6. Use
    `--allow-unchanged` to deploy a duplicate anyway.
  </Accordion>
  <Accordion title="unfinished release files were kept for inspection">
    An upload or unpack failed. Look with `shipdeck work`, then remove the files with
    `--cleanup`. The live release never stopped serving.
  </Accordion>
</Accordions>

## After the switch

<Accordions>
  <Accordion title="app api was not healthy within 20s">
    The `health.url` or your health commands did not pass in time. The URL is fetched from the
    server, so check the port and that the app listens on `127.0.0.1` or `0.0.0.0`. The release
    that was live before is put back according to `rollback.mode`.
  </Accordion>
  <Accordion title="this release was made before config format 2; deploy again">
    A rollback target has no `.shipdeck/settings.json`, so shipdeck cannot read what its setup
    needs. Deploy that version again with this shipdeck.
  </Accordion>
  <Accordion title="nothing was live before, so there is nothing to roll back to">
    A first deploy failed after the switch. The failed release stays live so you can look at it.
  </Accordion>
  <Accordion title="rollback failed">
    Putting the previous release back failed too. The server may be between two releases:
    inspect it with `systemctl status <process>`, the journal, and `shipdeck work`. The exit code
    is 5.
  </Accordion>
  <Accordion title="<id> stays live as you chose">
    You answered `n` to the rollback question, or `rollback.mode: off`. Roll back any time from
    the Releases screen or with `shipdeck rollback`.
  </Accordion>
</Accordions>
