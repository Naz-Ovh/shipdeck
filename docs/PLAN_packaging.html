Packaging shipdeck

Four ways in: cargo (install and binstall), npx, uvx, and one curl | sh script for everyone else. Linux gets the faster gnu build when its glibc is new enough, and a static musl build when it isn't.

Channels: cargo, npm, PyPI, curl script gnu first, musl fallback npm: @nhrs/shipdeck MIT OR Apache-2.0 glibc 2.28 floor · dist
  • Four channels. crates.io covers cargo install and cargo binstall, npm covers npx, PyPI covers uvx, and the install script covers everyone else, macOS included. Homebrew, .deb/.rpm, AUR and AppImage are out.
  • Linux gets two builds per architecture: gnu as the default, because it is faster, and static musl as the fallback. Every channel picks gnu when the machine has glibc 2.28 or newer.
  • The npm package is @nhrs/shipdeck, under your own npm account nhrs (Nazmul Hasan Rakib).
  • The license is MIT OR Apache-2.0, and dist drives releases with two custom jobs.
  • musl builds use mimalloc as their allocator. All other builds keep the default.
  • Channels ship one at a time: the install script first, then cargo, then npm, then uvx.

The README offers one install path: cargo install --git …. It needs a Rust toolchain and a few minutes of compiling. The repo has no CI, and the v<version> tags are pushed by hand for server-setup.sh. The code uses std::os::unix, so the targets are Linux and macOS. Windows users already run shipdeck inside WSL.

shipdeck ships under MIT OR Apache-2.0, the usual choice for Rust projects. Every registry accepts it, and users may pick either license; Apache adds a patent grant. Today Cargo.toml says license = "UNLICENSED" and publish = false, and crates.io refuses that. So stage 1 starts here: it adds LICENSE-MIT and LICENSE-APACHE, sets license = "MIT OR Apache-2.0". publish stays off until the cargo stage.

A tag push builds six binaries once and attaches them to a GitHub Release with checksums. The install script, the npm package and binstall all download those same files, so an install of "0.4.0" is the same binary whichever way it came. The v<version> tag you already push becomes the release trigger, and nothing else starts it, pull requests included.

Pushing the tag is the only step. You never make the release on GitHub: dist creates it only after every binary is built and checked, so a release is never public without its binaries, and a failed build makes no release at all. The docs site and, later, the registries run only after the release is published. dist writes the release notes; edit them afterwards if you like.

Two channels build their own copies from the same tag. crates.io takes the source, because cargo install compiles on the user's machine. PyPI needs wheels tagged for the platforms they run on, so maturin builds them in the release job. binstall reads crates.io only to find the version, then downloads the release archive.

gnu is the default on Linux because it runs faster, mostly thanks to glibc's memory allocator. A gnu binary only starts on a machine whose glibc is at least as new as the one it was built against. Built on GitHub's current Ubuntu runner, it would require glibc 2.39 or newer and refuse to start on Debian 12 or Ubuntu 22.04. So the gnu builds are compiled inside an old-glibc container on purpose. That container's version is the bottom of the supported range. Anything below it, and any musl system, gets the static musl build.

The floor is glibc 2.28. The gnu builds compile in the manylinux_2_28 container, the route dist's own docs take. Every glibc distro from the last seven years gets the gnu build: Debian 10, Ubuntu 20.04, RHEL 8 and everything newer.

The plan first set the floor at 2.17, using the manylinux2014 container. That broke during stage 1. GitHub runs actions such as checkout inside a job's container with its own Node, and that Node needs glibc 2.28, so a 2.17 container fails at its first step. zig, the other way to link against an older glibc, also defaults to 2.28, and dist never asks it for another version. Holding 2.17 would have meant wrapping how dist calls cargo, so you chose 2.28. What it gives up: CentOS and RHEL 7, Ubuntu 18.04 and Amazon Linux 2, all past end of life, get the musl build instead.

Who does the check

I read dist 0.33's installer templates to see what is already there. Its shell script tries the gnu archive first and runs check_glibc against the floor. Its npm package does the same with detect-libc. uv and pip do it through wheel tags. dist doesn't read the floor from the binary: it assumes the glibc of the machine that built it. So the floor is written into dist-workspace.toml as min-glibc-version, and the CI check below proves the binaries meet it. binstall is the gap: it checks that glibc exists, never which version. Below 2.28 it hands over a gnu binary that refuses to start with "GLIBC_2.28 not found". Those machines are all past end of life, and the install script gives them musl.

A CI step guards the floor. It reads each gnu binary's required glibc with the same ELF reader preflight already uses (build::GlibcVersion) and fails the release if a binary needs more than the floor. It runs after the builds and before the GitHub Release exists, so a binary that breaks the promise is never published.

Why the musl build failed on your machine

Nothing is wrong with musl or with shipdeck's code. aws-lc-sys, the crypto library under russh, compiles a C library while it builds, and C code built for musl needs a musl C compiler. Your machine doesn't have one, so the build stops before any Rust code is compiled. Setting an allocator can't help with that, because the allocator only matters once the program runs. Ubuntu's musl-tools package provides that compiler, and so does cargo-zigbuild, and CI installs it with one line. Switching russh to its ring backend wouldn't avoid it either, because ring compiles C as well. (The first draft wrongly listed ring as the way out.)

The allocator matters for speed, not for building. musl's malloc is the main reason musl builds run slower than gnu, so musl builds use mimalloc instead. gnu and macOS builds keep their default allocator. The fallback build then runs close to gnu speed. mimalloc's C code builds with the same musl compiler we need anyway, and the dependency exists only on musl targets:

[target.'cfg(target_env = "musl")'.dependencies] mimalloc = "0.1.52" #[cfg(target_env = "musl")] #[global_allocator] static GLOBAL: mimalloc::MiMalloc = mimalloc::MiMalloc;

dist drives releases. Its install script and npm package already do the gnu-or-musl check above, so we write none of that logic ourselves. We own two small custom jobs, one for crates.io and one for PyPI, and the release workflow is regenerated whenever dist updates.

[dist] ci = "github" targets = [ "x86_64-unknown-linux-gnu", "aarch64-unknown-linux-gnu", "x86_64-unknown-linux-musl", "aarch64-unknown-linux-musl", "x86_64-apple-darwin", "aarch64-apple-darwin", ] installers = ["shell", "npm"] npm-scope = "@nhrs" publish-jobs = ["npm", "./crates", "./pypi"] global-artifacts-jobs = ["./glibc-floor"] # the floor installers check; glibc-floor.yml proves the binaries meet it [dist.min-glibc-version] "*" = "2.28" # gnu builds run in an old-glibc container: that container sets the floor [dist.github-custom-runners.x86_64-unknown-linux-gnu] container = { image = "quay.io/pypa/manylinux_2_28_x86_64", host = "x86_64-unknown-linux-musl" } [dist.github-custom-runners.aarch64-unknown-linux-gnu] runner = "ubuntu-24.04-arm" container = { image = "quay.io/pypa/manylinux_2_28_aarch64", host = "aarch64-unknown-linux-musl" } [dist.github-custom-runners.aarch64-unknown-linux-musl] runner = "ubuntu-24.04-arm" # Linux and macOS, anyone curl -LsSf https://shipdeck.naz.ovh/install.sh | sh # Rust users cargo binstall shipdeck # prebuilt, no compiling cargo install shipdeck --locked # from source # run it without installing npx @nhrs/shipdeck ./scripts/deploy uvx shipdeck ./scripts/deploy

The npm package is @nhrs/shipdeck, because shipdeck on npm belongs to someone else. The command after install is still shipdeck; only the npx line shows the scope. dist's npm package downloads the matching release archive on install. If the install step was skipped, which pnpm does by default, it downloads on first run instead.

Channels ship one at a time, in the order the README lists them. Each stage ends with a tagged release that proves its channel works before the next one starts. The release tooling and the builds come first, because the install script needs them and everything after it reuses them.

Each registry needs an account in your name. We use trusted publishing wherever it exists (GitHub proves the workflow's identity, so no token is stored). crates.io and npm need one token for the very first publish, and after that it can be deleted.

The install script needs no account at all. Each of the others is needed only by the time its stage starts:

  • Before cargo: sign in to crates.io with GitHub and make a token for the first publish. Then turn on trusted publishing for both crates.
  • Before npm: the nhrs account already exists. You'll need a token for the first publish, then trusted publishing.
  • Before uvx: a PyPI account and a pending trusted publisher for project shipdeck. No token at all.
