# Releases: ids, layout, exit codes, the release workflow

What servers already depend on, and what the scripts that call shipdeck already depend on.
Both are contracts: add, never renumber or move.

## On the server

- Release ids and the `current`/`releases`/`backups`/`shared` layout are a contract with
  servers already deployed to. Change them only on purpose.
- Shipdeck's own files live in each release's `.shipdeck/`: `release.json`, `settings.json`,
  `<process>.service`, `<process>.pm2.json`, `oxfile.toml` and `nginx/<name>-<app>.conf`.
  The last two are not written yet: a deploy with `nginx:` or `oxmgr:` stops at preflight,
  so the plan carries no placeholder for them.
  Nothing else in the release is shipdeck's.
- `release.json` is written from `release.rs`; `settings.json` is the resolved deploy file,
  and a rollback reads it back through `Deployment::from_settings`. A release without it is
  refused: "this release was made before config format 2; deploy again".

## For scripts

- The exit codes in `console::run::exit_code` are a contract with the scripts that call
  shipdeck. Add new ones; never renumber.
- `--on-failure` maps onto `release.steps.rollback.mode`: `rollback` is `auto`, `keep` is
  `off`. A headless run never chooses `ask`.

## The release workflow

- `.github/workflows/release.yml` is generated by dist from `dist-workspace.toml`. Change the
  toml and run `dist generate`; never edit the yml by hand.
