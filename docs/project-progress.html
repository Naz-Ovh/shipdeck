    Where shipdeck is, and where it goes next

    shipdeck grows, one phase at a time, into a way to run your own servers: deploys, domains, databases, ready-made apps and mail. Words: a project is your own code that shipdeck deploys, like my-api. An app is a ready-made one that you host yourself, like n8n. Each item has an id, like p1b1. Copy it with the ⧉ button and paste it to an agent.

    Up next

    1. Server details can come from ${NAME} in the deploy file, a .env file, or -H, -P, -U for one deploy; --key is now --key-file (p0c8). Try it on a real server, then say yes or what to change.
    2. Config format 2 is built: a root file plus one deploy per deploy (a file or written in place), twelve steps, .shipdeck/ in each release, shipdeck tree, and binary with { path, to } (p0c7). The old format is refused. Nginx and oxmgr are parsed and stop a deploy at preflight.
    3. Owner: run the Podman SSH suite for config format 2 (docs/code/monorepo-ssh-tests.md). It is rewritten but unrun here: this machine has no container and no sshd.
    4. Monorepo deployment is built and verified through SSH in Podman: shared releases, saved app settings, rollback, controls, and logs (p1d3). Nginx and oxmgr remain future work.
    5. Static sites are built: static: next to service:, no process, and a stable path for nginx. Start with the plan and examples/static; the owner has not tried it yet (p4a0).
    6. The config file is now shipdeck.yaml or shipdeck.yml; deploy.yaml is no longer read. Existing projects need one mv (p0c6).
    7. The privileged-agent policy is built and verified in Podman: root-owned /opt/shipdeck/agent/v<version>/agent, sudo launch, same-major compatibility, newer-major refusal, atomic installs, and explicit app users (p3a1, p3d1). This needs a major release because the install and execution contracts changed. The owner must choose and publish the version.
    8. Agent completion remains verified: all ten findings in the agent completion review are fixed. A release still needs the four shipdeck-agent-* archives. Follow the agent completion plan and the handoff.
    9. Owner: answer the remaining decisions marked waiting: four for the desktop app (p2d1 to p2d4).
    10. Owner: five changes since version 0.6.1 are built but not released. They are Windows support (p0f2), release details with D (p0b3), wrapped log lines (p0e3), the check for Windows line endings (p0c4), and the end of support for pre-0.6 releases (p0c5). Try them, then say when to make a release.
    11. Owner: look at the spec page, spec.html (p1a1), and say yes or what to change. All the older planning pages are merged into it.
    12. Owner: click through the desktop mockup, desktop.html (p2a1), and say yes or what to change. This is the second take: everything starts from a server. The bar at the bottom of the page switches the theme and the network, shows the first run, picks how the next deploy ends, and opens each dialog.
    13. Owner: two questions about the settings backup (p1c6). Should the file be locked with a password? Should it also hold each project's shipdeck.yaml? And one about servers that stay connected (p1c7): how long until an unused one disconnects? Recommended: 10 minutes.
    14. Both the console commands (p1d1) and the TUI (p1d2) work through the engine now, over the pipe. Nothing runs the engine in its own process any more. Next: when an app closes, the engine finishes the step it is on (p1c2). The desktop app waits, as you asked.
